# Ручные проверки: первый прогон на тестовом стенде (2026-11-08)

Стенд: i5-10400 (Intel UHD 630) + RTX 3060, Windows 11 + Альт p11. Что уже проверено автоматически —
[`docs/test_stand.md`](../../../docs/test_stand.md). Здесь — то, что требует человека у стенда.

## Т-13. Альт не отвечает по SSH после перезагрузки из Windows

- **Зачем.** Дважды после перезагрузки Windows → Альт стенд отвечал на ping, порт 22 принимал соединение, но SSH не
  получал приветствия («banner exchange») больше часа: загрузка где-то стоит. После перезагрузки Альт → Альт всё
  работает. Без этого проверки Linux по SSH после Windows невозможны. Автоматика тут бессильна: нужен экран стенда.
- **Приоритет:** блокирует проверки Linux на стенде; 10–15 минут.
- **Подготовка.** Монитор на выход стенда.
- **Шаги.**
  1. Посмотрите на экран стенда, ничего не нажимая. Сфотографируйте его.
  2. Если на экране сообщение или запрос (проверка диска, «A start job is running…», пароль, экран входа) —
     сфотографируйте и только потом нажмите Enter / войдите.
  3. Когда SSH заработает, напишите мне — я сам посмотрю `journalctl -b` и что задержало загрузку.
- **На что смотреть.** Загрузка дошла до рабочего стола с автовходом или нет; есть ли текстовые сообщения.
- **Что прислать.** Фото экрана (шаги 1–2) — в `tests/manual/results/`.
- **Результат.** Пользователь: на экране был GRUB, выбрал Альт — загрузка пошла, SSH заработал.
- **Разбор.** По журналу GRUB не ждал: ядро стартовало через 1,5 мин после перезагрузки. 2 ч 25 мин стояла служба
  `plymouth-read-write` (заставка), а с ней `sysinit.target` и SSH. Двинулась через 4 с после подключения клавиатуры
  (переключатель USB). На экране оставался последний кадр GRUB, поэтому всё выглядело как ожидание в меню.
  Попутно нашлись часы на 8 ч позади (Windows: пояс UTC−8, аппаратные часы в местном времени) и сон GNOME через
  15 мин без ввода (стенд уснул посреди прогона NVK).
  **Что нашёл человек:** экран показал, где «стоит», а по журналу стало видно, что стоит не GRUB. Автоматика этого не
  ловила. Добавить в проверки: перед прогоном на стенде — `systemd-analyze` (время до `sysinit.target`) и проверка
  разницы часов.
- **Осталось сделать у стенда (системные настройки — за пользователем):**
  1. Альт: в `/etc/default/grub` из `GRUB_CMDLINE_LINUX_DEFAULT` убрать `splash`, затем `update-grub`.
  2. Альт, в сеансе ermaley: `gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-type 'nothing'`.
  3. Windows: часовой пояс «Москва»; в cmd от администратора
     `reg add HKLM\SYSTEM\CurrentControlSet\Control\TimeZoneInformation /v RealTimeIsUniversal /t REG_DWORD /d 1 /f`.
  После этого — одна перезагрузка Windows → Альт без человека у стенда, я проверю время загрузки.

## Т-14. Глазами: галерея на Intel и на NVIDIA (Windows)

- **Зачем.** Снимки на обеих картах совпали с эталонами WARP (≤ 2 единиц), но живой кадр на мониторе 21:9 — шрифты,
  размытие стекла, тени, плавность анимаций на ≤ 60 Гц — автоматика не оценивает.
- **Приоритет:** желательно до выпуска; 15 минут.
- **Подготовка.** Загрузить Windows на стенде. В `cmd`:
  ```
  cd /d C:\gran\gran
  set GRAN_ADAPTER=intel
  bin\gran_gallery.exe
  ```
  Затем то же с `set GRAN_ADAPTER=nvidia`.
- **Шаги.**
  1. Разверните окно на весь экран 3440×1440, прокрутите витрину до конца и обратно.
  2. Откройте `samples/glass.xml` (`bin\gran_gallery.exe samples\glass.xml`), подвигайте окно.
  3. Наведите курсор на кнопки и переключатели — анимации переходов.
- **На что смотреть.** Одинаковая картинка на обеих картах; нет мерцания, полос в градиентах, «лесенки» в тексте,
  рывков анимации; размытие стекла без артефактов по краям.
- **Что прислать.** Скриншоты с обеих карт, если видна разница или артефакт.
- **Результат.** Пользователь: не прошло. Видео в `tests/videos/`. Если быстро дёргать край окна, картинка
  не успевает отрисоваться, по краям чёрные и белые квадраты; после этого окно секунд на 5 зависает при попытке
  перенести. При первой записи экрана зависли оба выхода HDMI, системный блок пищал, понадобилась перезагрузка.
  На AMD основного компьютера почти не видно, и зависания нет.
- **Разбор.** Ошибка движка. Пока край тянут мышью, Windows крутит свой модальный цикл: каждое `WM_SIZE` уже
  перерисовано синхронно (`LiveResize`), но его событие RESIZE остаётся в очереди. После отпускания кнопки главный
  цикл проигрывал всю очередь: на каждое событие — ожидание GPU и `ResizeBuffers` под устаревший размер. Отсюда
  зависание на секунды, а пересоздаваемые буферы без кадра давали мусор на краях. Замер на 300 шагах (окно 480×320):
  без исправления Intel D3D12 — 2,8 с, Intel D3D11 — 1,0 с, NVIDIA — 0,4–0,7 с, AMD — до 0,9 с; с исправлением —
  около 1 мс везде. Исправление: размер цепочки берётся по нынешнему окну (`src/app/application_events.cpp`),
  устаревшие события пропускаются. Зависание HDMI в системных журналах Windows следов не оставило: ни сброса
  драйвера (TDR), ни аварийного выключения; вероятно, оно связано с той же лавиной пересозданий под захватом экрана.
  **Что нашёл человек:** зависание и мусор при перетаскивании — автотесты окно мышью не тянули. Добавлено:
  живой тест «live resize storm» (`tests/render/resize_live.cpp`) — 300 изменений размера внутри
  `WM_ENTERSIZEMOVE`…`WM_EXITSIZEMOVE` и предел 0,05 с на разбор очереди; без исправления он падает на всех картах.

## Т-15. Повторная проверка перетаскивания окна (Windows, Intel и NVIDIA)

- **Зачем.** Исправление Т-14 убрало зависание после перетаскивания (замер — 1 мс вместо секунд). Остались ли
  полосы на краях *во время* перетаскивания, автотест не видит: это кадры DWM.
- **Приоритет:** блокирует выпуск; 15 минут.
- **Подготовка.** Стенд в Windows; сборка с исправлением уже лежит в `C:\gran\gran\bin`. В `cmd`:
  ```
  cd /d C:\gran\gran
  set GRAN_ADAPTER=intel
  bin\gran_gallery.exe
  ```
  Затем то же с `set GRAN_ADAPTER=nvidia`.
- **Шаги.**
  1. Быстро потаскайте правый нижний угол окна 10–15 секунд, как в прошлый раз.
  2. Отпустите и сразу возьмите окно за заголовок, перенесите.
  3. Повторите с `bin\gran_gallery.exe samples\glass.xml`.
  4. Если захочется записать экран — сначала без записи (в прошлый раз запись совпала с зависанием HDMI).
- **На что смотреть.** Шаг 2: окно переносится сразу, без паузы. Шаг 1: есть ли ещё полосы по краям и насколько
  они заметнее, чем на AMD.
- **Что прислать.** «Зависает / нет»; видео, если полосы остались, — в `tests/videos/`.
- **Результат.** Пользователь: окно больше не зависает. Полосы по правому краю на обеих картах остались, видео
  (весь экран) — в `tests/videos/`.
- **Разбор.** На кадрах видео: растущая полоса справа белая сверху и чёрная снизу, а содержимое окна ещё
  старой ширины. DWM показывает окно нового размера раньше, чем приходит кадр GPU этого размера. В полосе тогда
  видна поверхность перенаправления окна, а окно её не закрашивало: `WM_PAINT` только вызывал `ValidateRect`, фон не
  стирался. Исправление: окно получает сплошной фон из разметки (`WindowDesc::background`), `WM_PAINT` идёт через
  `BeginPaint`, `WM_ERASEBKGND` закрашивает этим фоном (`src/platform/win32/win32_paint.cpp`). Полоса теперь — цвета
  фона окна, как у браузеров. Содержимое (карточки, текст) доходит до неё через кадр.
  Замер на стенде (`--resize-artifacts`, настоящая мышь, кадры монитора) до → после: Intel D3D12 120/376 → 0/372,
  Intel D3D11 88/386 → 0/361, NVIDIA D3D12 34/391 → 0/391, NVIDIA D3D11 28/405 → 0/399.
  **Что нашёл человек:** полосы во время перетаскивания. Тест Т-14 их не видел: он мерил только время после
  отпускания. Сначала не помогли и автоматические попытки: снимок GDI всегда показывал готовый кадр, а `SetWindowPos`
  из кода мусора не давал. Поймать удалось, только когда тест стал тянуть угол настоящей мышью туда-обратно и смотреть
  кадры монитора через Desktop Duplication. Добавлено: `gran_render_tests --hardware --resize-artifacts`
  (`tests/render/resize_artifacts.cpp`, `resize_drag.cpp`, `resize_duplication.cpp`) — без исправления падает
  на обеих картах. Он двигает курсор, поэтому запускается только на стенде. Глазами — Т-16.

## Т-16. Перетаскивание окна после исправления фона (Windows: Intel, NVIDIA, AMD)

- **Зачем.** Замер кадров монитора после исправления Т-15 чистый на Intel и NVIDIA, но он смотрит только на
  чисто белое и чисто чёрное. Остаётся ли заметная глазу полоса цвета фона, отстают ли карточки и текст, нет ли
  мерцания — видно только человеку. На AMD основного компьютера замер не запускался: он двигает курсор.
- **Приоритет:** блокирует выпуск; 15 минут.
- **Подготовка.** Стенд в Windows; сборка с исправлением уже лежит в `C:\gran\gran\bin`. В `cmd`:
  ```
  cd /d C:\gran\gran
  set GRAN_ADAPTER=intel
  bin\gran_gallery.exe
  ```
  Затем то же с `set GRAN_ADAPTER=nvidia`. На основном компьютере (AMD): `make` и `bin\gran_gallery.exe`.
- **Шаги.**
  1. Быстро подёргайте правый нижний угол окна туда-обратно 10–15 секунд, как в Т-15.
  2. Отпустите и сразу перенесите окно за заголовок.
  3. Повторите с `bin\gran_gallery.exe samples\glass.xml` (там фон тёмный, а стекло размыто).
- **На что смотреть.** Шаг 1: нет белых и чёрных полос; у края может на миг появиться полоса цвета фона окна — это
  ожидаемо, но скажите, насколько она заметна. Шаг 2: окно переносится сразу.
- **Что прислать.** «Есть полосы / нет» по каждой карте; видео, если что-то заметно, — в `tests/videos/`.
- **Результат.** Пользователь: полосы по бокам ушли на всех трёх картах (Intel, NVIDIA, AMD). Но на NVIDIA
  в какой-то момент при перетаскивании окно становится чёрным. Запись экрана программой этого не показывает,
  скриншоты тоже — видно только на камеру телефона (`tests/videos/phone.mp4`).
- **Разбор.** По кадрам с телефона: чёрной становится клиентская область окна витрины, а не весь экран. Заголовок
  и рабочий стол на месте, чёрное держится 1–2 с и возвращается несколько раз за 25 с. В системном журнале
  нет ни сброса драйвера, ни событий nvlddmkm. Оба монитора стенда подключены к NVIDIA (HDMI, 3440×1440, 85 Гц).
  У NVIDIA есть аппаратные слои: «MPO MaxPlanes: 4, MPO3, RGB», и включено аппаратное планирование (HAGS).
  У Intel мониторов нет: его кадры всегда копируются на NVIDIA и проходят через композицию DWM.
  Гипотеза: на NVIDIA цепочка обмена окна попадает на аппаратный слой (MPO, «hardware composed independent flip»).
  Тогда монитор показывает наш буфер в обход композиции DWM. Пересоздание буферов на каждом шаге перетаскивания
  сбивает слой, и он гаснет. Запись экрана видит отдельную композицию DWM, поэтому чёрного там нет. Это же объясняет,
  почему на Intel чёрного нет. Проверка — Т-17.

## Т-17. Отладка: чёрное окно на NVIDIA при перетаскивании (видно только глазами)

- **Зачем.** Запись экрана и снимки этого не ловят, а значит, и мои автотесты тоже: смотреть может только человек.
  Нужно отделить гипотезы:
  - (А) аппаратный слой MPO;
  - (Б) аппаратное планирование GPU (HAGS);
  - (В) конкретный API — у D3D12, D3D11 и Vulkan разные пути показа кадра.
  От ответа зависит исправление. Если подтвердится (А), план — не пересоздавать буферы на каждом шаге
  перетаскивания: держать их с запасом и менять только видимую часть (`SetSourceSize`). Это ещё и ускорит
  перетаскивание на Intel.
- **Приоритет:** блокирует выпуск; 30–40 минут (две перезагрузки).
- **Подготовка.** Стенд в Windows; сборка — в `C:\gran\gran\bin`. В `cmd`:
  ```
  cd /d C:\gran\gran
  set GRAN_ADAPTER=nvidia
  ```
  Каждый запуск ниже — одно и то же действие: 15 секунд дёргать правый нижний угол туда-обратно, затем 5 секунд
  просто держать окно неподвижно. Смотреть на монитор глазами (или на телефон).
- **Что уже снято без человека (PresentMon 2.6.0 на стенде, `C:\gran\tools\presentmon`).**
  - Режим показа каждого кадра на NVIDIA: замер `--resize-artifacts` (D3D12, D3D11) и галерея, которую водитель мыши
    (`C:\gran\drag.ps1`) дёргал 2 × 15 с с паузами. 1888 кадров, все — «Composed: Flip», ни одного «Hardware Composed:
    Independent Flip». В этом сценарии окно на аппаратный слой не уходит, и гипотеза (А) пока не подтверждена.
  - Программа записи экрана может сама выключать аппаратные слои, пока пишет. Тогда она не просто не видит чёрное,
    а убирает его причину. Поэтому важен шаг 0: запись режимов именно в тот момент, когда чёрное видно.
- **Шаги.**
  0. Запись режимов показа во время вашего перетаскивания (без записи экрана; PresentMon попросит права
     администратора):
     ```
     C:\gran\pm_manual.cmd --d3d12
     ```
     90 секунд дёргайте угол и отпускайте. Когда увидите чёрное, запомните время на часах Windows до секунды. Файл —
     `C:\gran\pm_manual--d3d12.csv`, я заберу его сам.
  1. Разные API, без изменений системы:
     ```
     bin\gran_gallery.exe --d3d12
     bin\gran_gallery.exe --d3d11
     bin\gran_gallery.exe --vulkan
     ```
     Отметьте для каждого: чёрное есть / нет и как часто.
  2. Отключить MPO (системная настройка — делаете вы; `cmd` от администратора), затем перезагрузка:
     ```
     reg add "HKLM\SOFTWARE\Microsoft\Windows\Dwm" /v OverlayTestMode /t REG_DWORD /d 5 /f
     ```
     Повторите шаг 1 (хватит `--d3d12` и того API, где чёрное было чаще всего).
  3. Вернуть MPO и перезагрузиться:
     ```
     reg delete "HKLM\SOFTWARE\Microsoft\Windows\Dwm" /v OverlayTestMode /f
     ```
  4. Только если шаг 2 не помог: выключить «Планирование графического процессора с аппаратным ускорением»
     (Параметры → Система → Дисплей → Графика → Дополнительные параметры графики), перезагрузка, повторить
     `--d3d12`. Затем включить обратно.
- **На что смотреть.**
  - Шаг 1: на каком API чёрное, появляется ли оно только во время движения или и после отпускания.
  - Шаг 2: если чёрное пропало, подтверждена (А).
  - Шаг 4: если пропало только здесь, подтверждена (Б).
- **Что прислать.** Таблицу «API × MPO вкл/выкл × чёрное да/нет». Видео с телефона — только если увидите новое,
  в `tests/videos/`.
- **Дополнительно (по желанию, если разрешите скачать).** PresentMon (Intel GameTechDev, GitHub) пишет режим показа
  каждого кадра: «Composed: Flip» или «Hardware Composed: Independent Flip». Тогда я сам на стенде увижу, уходит ли окно
  на аппаратный слой во время перетаскивания, без человека у монитора.
- **Результат шага 0.** Пользователь: записал PresentMon (`pm_manual--d3d12.csv`, 90 с) и видео на телефон
  с секундомером (`tests/videos/20009799322328.mp4`).
- **Разбор шага 0.**
  - Чёрное на видео — около 1,5 с подряд. Оно бывает и при запуске окна, и посреди перетаскивания: окно уже чёрное,
    а размер его всё ещё меняется. Всего за 90 с — около 8 раз.
  - В журнале PresentMon (4982 кадра) 12 провалов по 0,8–2,9 с: окно почти не вызывает `Present`, а сам `Present` при
    этом не блокируется (`msInPresentAPI` < 7 мс). Длительность и число провалов совпадают с чёрным на видео.
  - В автоматическом перетаскивании (`drag.ps1`) таких провалов нет, кроме запуска.
  - Аппаратный слой поймали дважды: 39 кадров «Hardware Composed: Independent Flip», оба раза на границе провала (запуск
    0,3–0,9 с, затем 76,7 с). На видео при запуске окно чёрное 2–3 с — ровно до следующего кадра в режиме «Composed».
  - Рабочая гипотеза: пока окно не шлёт кадров, DWM переводит его последний буфер на аппаратный слой NVIDIA. Слой
    гаснет, а запись экрана собирает свою композицию и чёрного не видит. Почему окно при ручном перетаскивании на
    секунду перестаёт рисовать — второй вопрос. Исключения кадра в `LiveResize` глотаются без записи в журнал;
    добавлю запись.
  - Попутно:
    - во время перетаскивания до экрана доходит лишь каждый четвёртый кадр, задержка показа около 50 мс (DWM не
      успевает), отсюда и отставание содержимого от края;
    - у запуска `--vulkan` в журнале галереи нет строки GPU — Vulkan на стенде, похоже, не стартует.
  - Следующий шаг — шаг 2: выключить MPO и повторить шаг 0 (`C:\gran\pm_manual.cmd --d3d12`), чтобы сравнить.
- **Результат шага 2.** Пользователь: с выключенным MPO (`OverlayTestMode=5`) чёрного нет. Окно открылось только через
  11 с. Видео — `tests/videos/20010187229912.mp4`.
- **Разбор шага 2.**
  - Гипотеза (А) подтверждена: в журнале PresentMon все 3827 кадров «Composed: Flip», чёрного на видео нет. Провалы
    без кадров остались (до 1,3 с), но теперь DWM сам показывает последний кадр. В журнале движка нет ни ошибок,
    ни медленных кадров перетаскивания.
  - 11 с до окна — это не движок. Галерея была пересобрана в 21:38, и это был первый запуск нового неподписанного
    exe. Microsoft Defender в 21:50:33 и 21:50:36 дважды запрашивал облачную проверку файла («при первом появлении»,
    до 10 с ожидания). Сам движок стартовал за 0,3 с: запуск в 21:50:34.04, первый кадр в 34.37. Повторный запуск того
    же exe — 18 мс до старта.
    Для стенда: исключение Defender для `C:\gran` (системная настройка, решает пользователь), иначе каждая
    пересборка даёт задержку первого запуска.
  - Почему гаснет при уходе со слоя. По прошлому журналу при запуске: 0,32–0,94 с кадры идут на аппаратный слой и
    показываются; на 0,94 с окно замолкает — и монитор чёрный до следующего кадра на 3,83 с. Цепочка D3D12 создана с
    `DXGI_SWAP_EFFECT_FLIP_DISCARD`, а этот режим разрешает выбросить содержимое буфера. Гипотеза (Г): когда DWM
    снимает молчащее окно со слоя и берёт буфер в композицию, буфер уже пуст. У D3D11 стоит `FLIP_SEQUENTIAL`, он
    содержимое хранит. На стенде собрана опытная галерея: `GRAN_FLIP_SEQUENTIAL=1` включает `FLIP_SEQUENTIAL` у D3D12
    (в репозитории этого нет).
  - Проба `CheckOverlaySupport` на выходе NVIDIA: все форматы (RGBA8, BGRA8, RGB10A2, FP16, NV12) объявлены одинаково,
    так что смена формата цепочки вряд ли поможет.
- **Шаг 5 (новый). MPO обратно включён; три запуска, каждый как в шаге 0 — 90 с, телефон, отметить чёрное.**
  1. Вернуть MPO (`cmd` от администратора), перезагрузка:
     ```
     reg delete "HKLM\SOFTWARE\Microsoft\Windows\Dwm" /v OverlayTestMode /f
     ```
  2. Как было: `C:\gran\pm_manual.cmd --d3d12`, затем переименуйте `C:\gran\pm_manual--d3d12.csv` в
     `pm_discard.csv`.
  3. Опыт (Г):
     ```
     set GRAN_FLIP_SEQUENTIAL=1
     C:\gran\pm_manual.cmd --d3d12
     ```
     Затем переименуйте CSV в `pm_sequential.csv`.
  4. D3D11 (там `FLIP_SEQUENTIAL` всегда): `C:\gran\pm_manual.cmd --d3d11`.
  - **На что смотреть:** есть ли чёрное в каждом из трёх запусков. Если в 3 и 4 его нет, а в 2 есть — (Г) подтверждена,
    и исправление — `FLIP_SEQUENTIAL` у D3D12 насовсем.
- **Результат шага 5.** Пользователь: чёрное во всех трёх запусках. В D3D11 — чаще и дольше, и у правого края
  появлялась серая грань.
- **Разбор шага 5.**
  - Гипотеза (Г) опровергнута: `FLIP_SEQUENTIAL` не помогает, а D3D11 (у него `FLIP_SEQUENTIAL` всегда) даже хуже.
  - PresentMon:

    | Запуск | Кадров | На аппаратном слое |
    |---|---|---|
    | discard | 5680 | 23, только при запуске |
    | sequential | 5845 | 174 — при запуске и на 33-й секунде |

  - Чёрное же видно много раз за 90 с, то есть и тогда, когда PresentMon пишет «Composed: Flip». Связь «чёрное =
    окно на слое» по журналу не прослеживается. Подтверждено одно: с выключенным MPO чёрного нет вовсе.
  - Значит, гаснет что-то в работе аппаратных слоёв NVIDIA вообще, а не только нашего окна. Следующий шаг (6) —
    сравнение: ведут ли себя так же чужие программы при таком же дёрганье края.
- **Шаг 6. Сравнение с другими программами (MPO включён, видео не нужно).** Так же 10–15 с дёргайте правый нижний

  1. Microsoft Edge — любая страница;
  2. Терминал Windows (Windows Terminal);

- **Результат шага 6.** Пользователь: у Edge, Терминала и Проводника чёрного нет, только у галереи. Видео края крупным

- **Разбор шага 6 и исправление.**
  - Чужие программы, которые показывают кадр через DirectComposition, не гаснут. Значит, ломается именно наш способ:
    цепочка, созданная прямо для окна (`CreateSwapChainForHwnd`), на NVIDIA с аппаратными слоями.
  - Исправление: движок показывает цепочку через DirectComposition, как Edge и Терминал. Цепочка для композиции
    (`CreateSwapChainForComposition`), а визуальный элемент DComp стоит поверх окна (`topmost`), поэтому GDI-фон из
    Т-15 остаётся под ним. Код — `src/rhi/dxgi/window_chain.cpp`, общий для D3D12 и D3D11. Если DirectComposition
    недоступна, работает прежний путь через HWND; `GRAN_PRESENT=hwnd` включает его вручную для сравнения.
  - Способ показа теперь пишется в строку GPU журнала: «… · DirectComposition» или «… · HWND».
  - Проверено на стенде:
    - в журнале оба API — DirectComposition, с `GRAN_PRESENT=hwnd` — HWND;
    - замер полос `--resize-artifacts`: 0 плохих кадров на Intel и NVIDIA, D3D12 и D3D11;
    - отладочные слои D3D12 (с GPU-Based Validation) и D3D11 молчат;
    - локально `make test` 343/343, `make test-render` D3D12/D3D11 на WARP — OK;
    - MSVC ASan на стенде (CMake, отладка): `ctest` 3/3 — модульные и рендер D3D12/D3D11 с живым окном, чисто.
  - Чёрное — только глазами, это Т-18.
  - **Что нашёл человек.** Чёрное окно, которого не видят ни запись экрана, ни снимки, ни Desktop Duplication, ни мои
    тесты. Без камеры телефона и опыта с выключением MPO причину было не найти.
  - Автоматически это не поймать: монитор показывает не то, что DWM отдаёт программам. В проверках остаются строка

- **Приоритет:** блокирует выпуск; 20 минут.
- **Подготовка.** Стенд в Windows, MPO включён (`OverlayTestMode` в реестре нет). Сборка — в `C:\gran\gran\bin`.

