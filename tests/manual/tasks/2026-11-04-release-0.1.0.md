# Ручные проверки к выпуску 0.1.0

Подготовлено: 2026-11-04. Охват: всё, что входит в 0.1.0 (этап 1 «Фундамент программ»), с упором на то, что
до сих пор проверялось только подачей сообщений из скрипта (`PostMessage`), а не живыми руками, и на работу с GPU.

## Т-1. Перетаскивание и захват указателя живой мышью

- **Зачем:** модель событий (1.1) проверена модульными тестами и синтетическими сообщениями; живое перетаскивание мышью
  не проверялось. Риски: порог 4 px не срабатывает или срабатывает при обычном щелчке, «залипший» захват после отпускания
  кнопки за пределами окна, мерцание подсветки зоны сброса.
- **Приоритет:** блокирует выпуск · ~10 минут.
- **Подготовка:** `bin\gran_gallery.exe samples\events.xml --debug`
- **Шаги и на что смотреть:**
  1. Перетащите карточку из левой колонки в правую. — Пока тянете, правая колонка подсвечена (состояние `DropTarget`),
     сама карточка — в состоянии `Dragging`; после отпускания карточка в правой колонке, строка статуса сообщила о переносе.
  2. Нажмите на карточку и отпустите, сдвинув мышь меньше чем на 3–4 пикселя. — Это щелчок, перетаскивание **не** начинается.
  3. Начните тянуть карточку и нажмите Esc, не отпуская кнопку. — Перетаскивание отменено, карточка на месте, подсветки нет.
  4. Начните тянуть карточку, выведите мышь **за пределы окна** и отпустите кнопку там; вернитесь в окно. — Ничего не
     «прилипло» к мыши, подсветки нет, следующий щелчок работает обычно.
  5. В поле «pad» (панель с координатами) нажмите кнопку мыши и, не отпуская, выведите мышь за окно и обратно. — Координаты
     в `pointerInfo` продолжают меняться и вне окна (захват указателя), после отпускания — перестают.
  6. Нажмите «Сбросить доску». — Карточки вернулись в исходные колонки.
  7. Щёлкните правой кнопкой по «pad» — открылось меню «Очистить координаты»; пункт работает.
- **Что прислать:** «прошло/нет» по каждому шагу; при ошибке — короткое видео (Win+Alt+R в Xbox Game Bar) или скриншот
  и последние строки журнала.

## Т-2. Выделение в списках: Shift и Ctrl живой мышью, проверка в отладчике

- **Зачем:** при проверке 1.7 Shift через `PostMessage` до окна не доходил, поэтому диапазонное выделение проверено только
  модульными тестами. Гипотеза: состояние модификаторов в событии мыши берётся верно. Проверяем руками и отладчиком.
- **Приоритет:** блокирует выпуск · ~15 минут.
- **Подготовка:** `bin\gran_gallery.exe samples\models.xml --debug` под отладчиком IDE (сборка `make DEBUG=1 all`).
- **Шаги и на что смотреть:**
  1. В списке заказов щёлкните первую строку, затем Shift+щелчок по пятой. — Выделены строки 1–5, текущая — пятая.
  2. Ctrl+щелчок по третьей. — Третья снята, остальные остались; Ctrl+щелчок по седьмой — добавилась.
  3. Стрелка ↓ с зажатым Shift. — Диапазон расширяется от опорной строки; Ctrl+A — выделено всё.
  4. В дереве отделов: «+»/«−» и стрелки ←/→ раскрывают и сворачивают ветки; выделение строки сохраняется.
  5. Введите в поле «Клиент или город» часть названия. — Список фильтруется, выделенные записи, оставшиеся в списке,
     остаются выделенными.
  6. **Отладчик:** точка останова в начале `SelectionModel::activate` (`src/data/selection_click.cpp:37`).
     Сделайте обычный щелчок, Shift+щелчок и Ctrl+щелчок.
- **Что сообщить:** для шага 6 — значения `index`, `control`, `shift` при каждом из трёх щелчков и сколько раз сработала
  точка на один щелчок (ожидаю ровно 1 раз и `shift=true` только при Shift). Для шагов 1–5 — «прошло/нет».

## Т-4. Захват кадра D3D12 в RenderDoc

- **Зачем:** главный риск кода, написанного моделью, — ошибки GPU, которые не роняют программу: лишние или непарные
  барьеры, выход числа экземпляров за ёмкость буфера, неверное смешивание. Отладочный слой ловит не всё; захват кадра
  показывает, что GPU делает на самом деле, на вашей видеокарте AMD.
- **Приоритет:** блокирует выпуск · ~30 минут.
- **Подготовка:** RenderDoc 1.x (renderdoc.org). В RenderDoc: *File → Launch Application*, Executable —
  `C:\tmp\Gran UI\bin\gran_gallery.exe`, Working Directory — `C:\tmp\Gran UI`, Command-line Arguments — `samples\glass.xml --d3d12`.
  *Launch*, в окне программы подвигайте мышью над кнопками, нажмите **F12** (захват), повторите для `samples\showcase.xml`.
- **На что смотреть (в захвате):**
  1. **Event Browser:** сколько вызовов отрисовки (`DrawInstanced`) в кадре и между ними — проходы размытия подложки
     (для glass). Запишите число вызовов и число барьеров (`ResourceBarrier`).
  2. **Барьеры:** у буфера кадра swapchain переход `PRESENT → RENDER_TARGET` в начале и обратно `RENDER_TARGET → PRESENT`
     в конце; у текстур размытия каждая пара «стал целью отрисовки → стал источником для шейдера» парная, без «лишних»
     переходов в то же состояние.
  3. **Pipeline State → Output Merger:** смешивание предумноженной альфой — Src = `ONE`, Dest = `INV_SRC_ALPHA`.
  4. **Mesh/Buffer viewer** у главного `DrawInstanced`: `InstanceCount` и размер буфера экземпляров — число экземпляров
     × размер структуры (заголовок `GpuInstance`) не больше размера буфера.
  5. **Texture Viewer:** атлас глифов — чёткие глифы без мусора и наложений; текстуры картинок — без полос и сдвигов строк.
  6. **Performance Counters / Timeline** (если доступно на AMD): время кадра на GPU.
- **Что прислать:** два файла `.rdc` (путь в `tests/manual/results/2026-11-04/`), скриншот Event Browser, ответы по пунктам 1–6.
  Всё непонятное — тоже присылайте, разберу сам.

## Т-5. Потеря устройства: принудительный TDR

- **Зачем:** код восстановления есть (`recreateGraphics` в `src/app/application_frame.cpp:95`: бэкенд сообщает
  `DEVICE_LOST`, окно пересоздаёт графику из сцены на CPU), но живьём он не проверялся ни разу. Сбой драйвера у
  пользователей программ — реальный сценарий.
- **Приоритет:** до выпуска · ~15 минут.
- **Подготовка:** `dxcap.exe` входит в «Средства графики» Windows (*Параметры → Система → Дополнительные компоненты →
  Средства графики*). Запустите `bin\gran_gallery.exe samples\showcase.xml --debug`. В консоли **администратора**:
  `dxcap -forcetdr`.
- **Шаги и на что смотреть:**
  1. После `dxcap -forcetdr` экран мигнёт (это сброс драйвера). — Окно галереи через секунду-две снова рисует ту же
     картинку, программа не закрылась, ввод работает (наведение, поле ввода, анимации).
  2. Повторите с `--d3d11` вместо `--debug`.
  3. Откройте журнал `%LOCALAPPDATA%\GranGallery\logs` — есть ли запись о потере устройства и её причине.
  4. Если окно не восстановилось или программа закрылась — повторите под отладчиком с точкой останова на
     `src/app/application_frame.cpp:95` и сообщите, сработала ли она; если нет — в каком месте выброшено исключение

## Санитайзеры

Linux (WSL Ubuntu 26.04, GCC 15.2), `make DEBUG=1 SANITIZE=address,undefined test`, `ASAN_OPTIONS=detect_leaks=1`:

1. Первый прогон — **найдена ошибка**: UBSan `src/app/window_layout.cpp:98: reference binding to null pointer of type
   'struct Application'` в тесте `testCloseWithResult` (`tests/src/app/window_owner_tests.cpp:117`). `saveState` сразу
   разыменовывал `State::owner`, а модульные тесты оконного слоя создают `State` без программы. В настоящей программе
   `owner` задан всегда (конструктор `Application`), поэтому у пользователей это не проявлялось, но это неопределённое
   поведение. Исправлено: `saveState` без программы ничего не сохраняет.
2. Повторный прогон — 332/332 (на Linux нет 5 тестов окон Win32), ни одного сообщения ASan, UBSan и LeakSanitizer.

Valgrind memcheck (сборка `DEBUG=1` без санитайзеров, `--leak-check=full --track-origins=yes`, с исправлением из п. 1):
332/332, `ERROR SUMMARY: 0 errors`, без «definitely/indirectly lost».

Ограничение: санитайзеры и Valgrind проходили модульные тесты, то есть код ядра без живого окна и без драйвера
видеокарты. Окно, ввод и GPU в долгой работе — задачи Т-1…Т-8 выше.
