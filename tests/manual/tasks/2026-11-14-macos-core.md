# Ручные проверки: ядро на macOS (шаг M3), 2026-11-14

Что сделано: на macOS собирается ядро без окна ОС (Makefile — `gmake`, CMake — в том числе универсальная сборка
x86_64 + arm64), все модульные тесты идут на безоконной платформе; сборка без платформы ОС (`NATIVE=0` /
`-DGRAN_NATIVE=OFF`) работает и на Linux. Отчёт о сбое получил ветку macOS (регистры из `uc_mcontext->__ss`, образы dyld
вместо `/proc/self/maps`). Workflow `.github/workflows/macos.yml` проверяет это на раннере macOS 15 при каждом push.

Автоматика у меня (машины с macOS нет):
- WSL, clang 21, `make NATIVE=0 all test test-crash bindings` и CMake `-DGRAN_NATIVE=OFF` + ctest — результат в журнале;
- проверка синтаксиса всего кода с 64-битными типами как на macOS (`uint64_t` = `unsigned long long`, а `size_t` —
  `unsigned long`: на Linux это один тип, и ошибки вида `std::min(u64, size_t)` там не видны);
- родная сборка Linux (GCC, Vulkan/X11) и Windows `make test` — не сломаны.

Чего не проверить без раннера: libc++ вместо libstdc++, заголовки SDK macOS (`<sys/ucontext.h>`, `<mach-o/dyld.h>`),
поведение сигналов на macOS, Rosetta. Это покажет первый прогон workflow — а для него нужен push (только по вашей команде).

## Т-47. Первый прогон workflow macOS на GitHub

- **Зачем.** Код ветки macOS (отчёт о сбое, Makefile под Darwin, CMake с `CMAKE_OSX_ARCHITECTURES`) ни разу не
  компилировался настоящим Apple clang и SDK. Только раннер покажет, собирается ли ядро и проходят ли тесты на libc++.
- **Приоритет:** блокирует выпуск 0.2.0 (M3 входит в 0.2.0) · ~5 минут вашего времени + ~15 минут прогона.
- **Подготовка.** Коммит с M3 в `main` (готовлю я). Push — по вашей команде: `git push origin main` и
  `git push gitverse main` (на Gitverse workflow macOS не запускается — там раннер только Linux).
- **Шаги.**
  1. Скажите «пушь» (или отправьте сами).
  2. Откройте на GitHub вкладку Actions → workflow «macOS» → прогон этого коммита.
  3. Дождитесь обеих задач: «macOS arm64 (Makefile)» и «macOS universal (CMake)».
- **На что смотреть.**
  - Обе задачи зелёные. В шаге «Ядро, примеры, тесты» — строка `Итого: N тестов, пройдено N, упало 0`
    (N — как на Linux, 434: тесты HWND только Windows).
  - Шаг «Отчёт о сбое»: `segv`, `terminate`, `abort` — `text 1, companion 1`, затем `crash reports OK`.
  - Шаг «Общая библиотека C ABI» печатает число экспортов `_gran_…` больше нуля.
  - Задача CMake: `lipo` не упал (в тестовой программе две архитектуры), ctest — все тесты, x86_64 через Rosetta — тоже.
  - Признаки ошибки: красная задача; предупреждения компилятора в журнале (`warning:`) — тоже пришлите, даже если сборка
    прошла: на Windows и Linux их сейчас ноль.
- **Что прислать.** Ссылку на прогон (или просто «прошло»). Если упало — ссылку; журнал я прочитаю сам через API
  (`https://api.github.com/repos/ErmaleyAlekov/Gran-UI/actions/runs?head_sha=<sha>`), артефакты с отчётами о сбое
  (`macos-make-reports`, `macos-cmake-reports`) прикладываются автоматически.

## Т-48. Ревью: ветка macOS в отчёте о сбое и логика `NATIVE` в сборке

- **Зачем.** Ветка macOS в обработчике сигналов не исполнялась ни разу, а ошибка в нём видна только при настоящем падении
  у пользователя. Логику переключателей сборки легко сломать в редком сочетании ОС и флагов.
- **Приоритет:** когда будет время · ~30 минут.
- **Подготовка.** Файлы:
  - `src/log/crash_posix_context.cpp` — `readRegisters` и `writeModules` (Linux и macOS);
  - `src/log/crash_posix_report.cpp` — `writeRegisters`, `writeStackBytes`;
  - `Makefile` — блоки «Определение ОС», `NATIVE`/`VULKAN` по умолчанию, «Платформенные особенности», проверки сочетаний;
  - `CMakeLists.txt` (опция `GRAN_NATIVE`), `cmake/GranSources.cmake`, `cmake/GranOptions.cmake`;
  - `src/platform/none/none_platform.cpp`, `src/rhi/none/platform_backend.cpp`.
- **Шаги / на что смотреть.**
  1. Обработчик сигнала: только async-signal-safe вызовы? `_dyld_*` формально не входят в список — я записал довод
     в комментарии; согласны ли вы, или лучше собирать список образов заранее (при установке) и обновлять колбэком
     `_dyld_register_func_for_add_image`?
  2. arm64 macOS: регистры читаются макросами `__darwin_arm_thread_state64_get_pc/sp/fp` — верно ли для arm64e
     (подписанные указатели)?
  3. Дамп стека кусками по 4 КБ: на Apple Silicon страница 16 КБ — рассуждение «куски не пересекают границу
     отображения» остаётся верным? (Я считаю, что да: граница 16 КБ кратна 4 КБ.)
  4. Сборка: найдите сочетание ОС и флагов (`NATIVE`, `VULKAN`, `DEBUG`, `SANITIZE`, `CXX`), при котором Makefile или
     CMake молча собирают не то (например, бэкенд без окна или окно без бэкенда) вместо понятной ошибки.
  5. На macOS `DEBUG=0` больше не даёт `-s` при компоновке (ld64 считает ключ устаревшим): нужен ли там шаг `strip`?
- **Что прислать.** Ссылки `файл:строка` с замечаниями.
- **Результат.** Использование _dyld_* в crash_posix_context.cpp:58-77 оправдано и надёжно на практике, переходить на колбэки регистрации образов не нужно. Чтение регистров через __darwin_arm_thread_state64_get_* (crash_posix_context.cpp:41-44) корректно снимает PAC-подпись на arm64e, а дамп стека кусками по 4 КБ (crash_posix_report.cpp:52-66) остаётся безопасным на 16-килобайтных страницах Apple Silicon благодаря кратности. В обработчике сигнала (crash_posix_report.cpp:80-81) стоит добавить лишь проверку info != nullptr перед обращением к info->si_addr. В системе сборки критичных расхождений нет, но при NATIVE=0 (Makefile:240-244, CMakeLists.txt:154-225) молча собираются нерабочие GUI-примеры и gran_c со стабами, выбрасывающими исключения. Отдельный шаг strip на macOS при DEBUG=0 (Makefile:100-104) добавлять не нужно, так как DWARF-отладка остаётся в .o, а сохранение таблицы символов необходимо для работы backtrace_symbols_fd.

  **Разбор (Claude, 2026-11-14).** Пункты 1–3 и 5 — согласен, без изменений (`_dyld_*`, макросы PAC, куски по 4 КБ,
  без `strip`: таблица символов нужна `backtrace_symbols_fd`). Исправлено:
  - `info == nullptr` в `writeSignalReport` — адрес 0 вместо разыменования (`crash_posix_report.cpp`);
  - `NATIVE=0` больше не собирает нерабочие программы: примеры (всем нужно окно или GPU) исключены в Makefile и CMake,
    `make bindings` — отказ с понятным текстом, в CMake `GRAN_BUILD_BINDINGS` по умолчанию = `GRAN_NATIVE`, явный ON при
    `GRAN_NATIVE=OFF` — ошибка конфигурации; `gran_rcc` теперь собирается в `all` и без примеров.
  Сам при проверке нашёл: скобки в `@echo` цели `bindings` ломали `sh` (`Syntax error: "(" unexpected`) — убраны.
  **Что нашёл человек и чего не поймала автоматика:** нулевой `info` не встречается в тестах (сбой всегда настоящий
  SIGSEGV/abort), а «молча собранные нерабочие программы» — не ошибка сборки, её видит только тот, кто запустит пример.
  В автоматику: CI `linux.yml` собирает ядро `NATIVE=0` без пакетов X11 и Vulkan — зависимость от них станет ошибкой.
