## Т-53. Архив MSVC в своём проекте Visual Studio

- **Зачем.** Архив `…-windows-x86_64-msvc.zip` собирается CMake с `/MT`; программа заказчика может быть с `/MD`,
  Debug или другой версией MSVC — тогда компоновщик выдаст `LNK2038` (несовпадение рантайма или `_ITERATOR_DEBUG_LEVEL`).
  Нужно понять, хватает ли одного архива Release `/MT` или нужны ещё Debug и `/MD`.
- **Приоритет:** до выпуска 0.2.0 · ~30 минут.
- **Подготовка.** После первого ручного запуска workflow `Release` на GitHub (Actions → Release → Run workflow, ветка
  `main`) — скачать артефакт `release-preview` и распаковать `gran-ui-0.2.0-dev-windows-x86_64-msvc.zip`.
  Либо собрать архив локально в Git Bash из корня Грани:
  ```bash
  bash tools/release/build_windows.sh msvc "C:/tmp/Dom lib C++" dist
  ```
- **Шаги.**
  1. Новый проект «Консольное приложение C++» в Visual Studio 2026, стандарт C++17, x64, Release.
  2. Добавить в проект файлы `examples/snapshot/*.cpp` и `snapshot.hpp` (из исходников Грани — как «чужую» программу).
  3. Каталоги включаемых файлов — `<архив>/include`; библиотеки — `<архив>/lib/gran.lib`, `beresta_static.lib` и
     системные `d3d11.lib d3d12.lib dxgi.lib dxguid.lib dwmapi.lib shcore.lib imm32.lib uiautomationcore.lib
     oleaut32.lib ole32.lib uuid.lib user32.lib gdi32.lib shell32.lib`.
  4. Собрать с рантаймом `/MT` (Свойства → C/C++ → Создание кода) и запустить:
     `snapshot.exe <архив>/samples/showcase.xml shot.png 1200 760`.
  5. Переключить рантайм на `/MD`, пересобрать. Затем конфигурацию Debug (`/MTd`), пересобрать.
- **На что смотреть.** Шаг 4: сборка без ошибок, `shot.png` — витрина как в `docs/images`. Шаг 5: какие ошибки
  компоновщика (`LNK2038` и др.) — ожидаемо есть; важно, понятны ли они без чтения исходников.
- **Что прислать.** Текст ошибок шага 5 (первые 10 строк), `shot.png` шага 4; ваше мнение: нужен ли в выпуске архив
  с `/MD` и Debug.
- **Результат.** Выполнено Claude 2026-11-16 по просьбе пользователя («остальные задачи ты и без меня можешь сделать»),
  без IDE Visual Studio: тот же `cl.exe` (MSVC 19.51) из командной строки, пример `snapshot` как чужой проект
  (`scratchpad`, `build.bat`). Архив `…-msvc.zip`: `/MT` — собирается и снимает кадр; `/MD` — `LNK2038`
  «RuntimeLibrary: MT_StaticRelease ≠ MD_DynamicRelease»; `/MTd` — `LNK2038` «_ITERATOR_DEBUG_LEVEL 0 ≠ 2» и
  «MT_StaticRelease ≠ MTd_StaticDebug». Ошибки понятны, но новый проект Visual Studio по умолчанию — `/MD`/`/MDd`, то
  есть с одним архивом `/MT` пользователь упирается в ошибку сразу.
- **Разбор.** Одного архива мало. Добавлены опция CMake `GRAN_MSVC_DYNAMIC_RUNTIME` (`/MD`; «Берёсте» выключается свой
  статический рантайм, иначе подпроект оставался на `/MT`), режим `build_windows.sh msvc-md` и архив
  `…-windows-x86_64-msvc-md.zip` в `release.yml`. Проверено: с `msvc-md` пример собирается в Release `/MD` и в отладочном
  варианте `/MD /Od /Zi /D_ITERATOR_DEBUG_LEVEL=0`, оба снимают кадр. Отладочные библиотеки в выпуск не кладутся (размер
  удвоился бы, у Gitverse предел 100 МБ на файл; архив сейчас ~23 МБ) — способ подключить в Debug описан в
  `docs/building.md`, «Готовые архивы выпуска». **Что нашёл человек:** задачу ставил он — вопрос «хватает ли одного /MT»
  без неё не возник бы. **В автоматику:** сборка потребителя с `/MD` против архива — кандидат в шаг `release.yml`.

## Т-54. Архив Linux на системе без исходников (Альт p11 / Astra)

- **Зачем.** Архив Linux собран в Astra 1.7 и должен работать на всех более новых системах. Проверка — на машине,
  где Грань и «Берёста» не собирались: хватает ли архива, системных пакетов и `gran_snapshot` из `bin/`.
- **Приоритет:** до выпуска 0.2.0 · ~30 минут.
- **Подготовка.** Стенд Альт p11 (`ssh gran-alt`) или рабочий стол Astra Fly. Архив
  `gran-ui-0.2.0-dev-linux-x86_64-gcc10.tar.gz` (Альт p11, GCC 13) или `…-gcc8.tar.gz` (Astra 1.7, GCC 8) — из артефакта `release-preview` (как в Т-53) или из
  `scratchpad` этой сессии (путь назову). Пакеты: `g++ make libX11-devel libvulkan-devel` (Альт), `mesa-vulkan-drivers`
  для программного Vulkan.
- **Шаги.**
  1. `tar -xzf gran-ui-*-linux-x86_64-gcc*.tar.gz && cd gran-ui-*-linux-x86_64-gcc* && cat BUILD_INFO.txt`
  2. `./bin/gran_snapshot samples/showcase.xml /tmp/shot.png 1200 760` — на видеокарте; затем с
     `VK_ICD_FILENAMES` на lavapipe, если есть.
  3. Собрать пример как свою программу (исходники `examples/snapshot/` скопировать с машины разработки):
     `g++ -std=c++17 -Iinclude snapshot/*.cpp lib/libgran.a lib/libberesta.a -lX11 -ldl -pthread -o snap`
     (на GCC 8 добавить `-lstdc++fs`), запустить как в шаге 2. Архив — под свой компилятор: `gcc8` только для GCC 8,
     `gcc10` для GCC 10+ (docs/building.md, «Почему архивов Linux два»; в контейнерах проверено: GCC 12 Astra 1.8 и
     GCC 13 Альт p11 с `gcc10`).
  4. `python3 -c "import ctypes; print(ctypes.CDLL('./lib/libgran_c.so').gran_abi_version())"`.
- **На что смотреть.** Шаг 2–3: кадр без ошибок, шрифты подобраны (на Альт нет Segoe — должна сработать замена).
  Шаг 3: нет ошибок компоновки про `GLIBC_`/`GLIBCXX_`. Шаг 4: число версии ABI, без ошибки загрузки.
- **Что прислать.** `/tmp/shot.png`, вывод `cat BUILD_INFO.txt`, ошибки, если были.
- **Результат.** Выполнено Claude 2026-11-15…16 в контейнерах Docker (машин без исходников, как просила задача): архив
  `gcc10` — пример `snapshot` собран GCC 13 (Альт p11) и GCC 12 (Astra 1.8), кадры сняты; архив `gcc8` — собран GCC 8.3
  (Astra 1.7, с `-lstdc++fs`), кадр снят, `bin/gran_snapshot` и `libgran_c.so` (`ctypes`, `gran_abi_version() == 1`)
  работают и на Astra 1.7, и на Альт p11.
- **Разбор.** Прошло. Найдено по пути: инструментам из `bin/` нужен системный `libX11` (на Альт p11 в чистом образе его
  нет — `libX11.so.6: cannot open shared object file`); это ожидаемо для оконной сборки — список пакетов для запуска
  добавлен в `docs/building.md`. Живой рабочий стол (Astra Fly) не проверялся — только кадры вне экрана.

## Т-57. Ревью: слой путей `gran::fs`

- **Зачем.** Новый код на границе с ОС: перевод UTF-8 ↔ UTF-16, `FindFirstFileExW`, `lstat`/`stat`, обход папок,
  замена файлов. Ошибки здесь — утечка дескриптора поиска, зацикливание на ссылке, переполнение при переводе времени,
  потеря файла при неудачной замене.
- **Приоритет:** до выпуска 0.2.0 · ~45 минут.
- **Подготовка.** Файлы: `include/gran/utils/file_system.hpp` (контракт), `src/utils/fs/*.cpp`; места использования —
  `src/settings/settings_file.cpp` (сохранение через .tmp и замену), `src/log/log_rotate.cpp`, `src/res/manifest_folder.cpp`.
- **Шаги / на что смотреть.**
  1. `wide_path_windows.cpp`: все ли проверки — до `static_cast` к `int`; верно ли переводится `FILETIME` и что будет с
     временем до 1970 и после 2262 года.
  2. `file_system_windows.cpp` / `file_system_posix.cpp`: закрывается ли дескриптор при исключении; что вернёт
     `queryPath` для висячей ссылки, точки соединения (junction), устройства (`NUL`, `/dev/null`).
  3. `file_list.cpp`: может ли обход зациклиться или уйти в бесконечную рекурсию; что с длинными путями (> 260 символов).
  4. `path_join.cpp`, `path_root.cpp`: `normalizePath` и `joinPath` на краях — `C:`, `//сервер`, `/..`, пустые строки.
  5. `settings_file.cpp`: при сбое `renamePath` старые настройки не теряются?
- **Что прислать.** Замечания `файл:строка` — что не так и пример входа.
- **Результат.** в file_system_windows.cpp, где GetFileAttributesExW читает атрибуты самой ссылки вместо цели, из-за чего висячие симлинки считаются существующими обычными файлами (в отличие от POSIX), а длинные пути свыше 260 символов не обрабатываются. В path_join.cpp и path_root.cpp есть мелкие краевые нестыковки на Windows при склейке сетевых путей //server с корневым /sub и обработке тройных ведущих слешей. При сохранении настроек в settings_file.cpp старый файл при сбое renamePath не теряется, но нужно обязательно вызывать output.close() до проверки потока, иначе ошибка сброса буфера при закрытии файла может затереть рабочие настройки битым файлом, а при ошибке самой записи не удаляется .tmp
- **Разбор (Claude, 2026-11-16).** Все замечания по делу, исправлено:
  1. `file_system_windows.cpp` `queryPath`: у точки повторной обработки метка читается с самой точки
     (`FILE_FLAG_OPEN_REPARSE_POINT`); символическая ссылка и точка соединения — сведения о цели через `CreateFileW`
     (вся цепочка), висячая — `exists == false`, `link == true`, как `stat` на POSIX. Заглушки облака (OneDrive) — обычные
     файлы и папки. `listDirectory` берёт метку из `dwReserved0`. `removePath` решает по атрибутам самого пути и удаляет
     ссылку, а не цель. Новый файл `system_path_windows.cpp`.
  2. Длинные пути: `internal::systemPath` — от 240 байт путь становится абсолютным нормализованным в форме `\\?\`
     (`\\?\UNC\` для сетевого); через неё идут все вызовы ОС, потоки и `MappedFile`.
  3. `joinPath("//srv/share", "/sub")` → `//srv/sub` (имя корня base, как у std::filesystem); тройные ведущие
     разделители на Windows — корень без имени, как «/a» (поведение закреплено тестом).
  4. `settings_file.cpp`: `close()` до проверки, `.tmp` удаляется при любой ошибке; то же место нашлось в `gran_rcc`
     (`writeIfChanged`) — исправлено.
  Тесты: `tests/src/utils/file_system_edge_tests.cpp` (путь > 300 символов; висячая ссылка — на Linux, на Windows без
  режима разработчика ссылку создать нельзя; точка соединения `mklink /J` на Windows), новые случаи в `path_text_tests.cpp`.
  Попутно: `std::filesystem::remove_all` из libstdc++ MinGW зависает на дереве длиннее 260 символов — тесты чистят папки
  самим слоем. **Что нашёл человек и не поймала автоматика:** все четыре класса — тестов на ссылки, длинные пути и сбой
  записи не было, санитайзеры такие ошибки не видят. **В автоматику:** перечисленные тесты.
