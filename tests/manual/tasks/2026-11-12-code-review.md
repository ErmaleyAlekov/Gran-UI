# Ревью кода: разбор недоверенных файлов (PNG/inflate, TrueType), 2026-11-12

Первая задача нового вида — ревью кода (правило `human_review.md`, раздел 3). Аудит 2026-11-12 прошёл эти файлы
clang-tidy и глазами и ошибок не нашёл, но это самые рискованные места движка: байты приходят из чужого файла
(картинка из сети, шрифт пользователя), а модульные тесты покрывают только корректные и несколько заведомо битых
входов. Фаззинга пока нет (П.7). Свежий взгляд программиста здесь ценнее ещё одного прогона анализатора.

## Т-41. Ревью: распаковка PNG (inflate) и разбор глифов TrueType

- **Зачем.** Найти чтение или запись за границей буфера, переполнение в вычислении размера или смещения, бесконечный
  цикл и рекурсию без предела на специально испорченном файле. ASan видит такое только на тех входах, что есть в тестах.
- **Приоритет:** желательно до выпуска 0.2.0 · ~40–60 минут (≈ 600 строк).
- **Подготовка.** Код в `main`. Файлы по порядку (данные идут сверху вниз):
  1. `src/image/png_chunks.cpp` — куски PNG, длины, CRC, размеры (пределы — `include/gran/image/image.hpp`).
  2. `src/image/inflate.cpp`, `inflate_blocks.cpp`, `inflate_tables.cpp`, `inflate_bits.cpp` — DEFLATE (по
     алгоритму puff из zlib): таблицы Хаффмана из длин кодов, расстояния назад, копирование.
  3. `src/image/png_unfilter.cpp` — фильтры строк (Paeth и др.), шаг байта на пиксель.
  4. `src/text/font/font_loca.cpp`, `font_glyf.cpp`, `font_composite.cpp` — смещения глифов, точки контуров,
     составные глифы (ссылки глифа на глифы). Чтение — через `FontReader` (`src/text/font/font_reader.cpp`:
     за границей возвращает 0).
- **Шаги — на что смотреть в коде.**
  1. Каждое число из файла (длина, счётчик, смещение, индекс) — проверено ли до использования как индекс, размер
     `resize`/`assign` или смещение указателя? Проверка вида `pos + len > size` (переполняется) вместо `len > size - pos`?
  2. Арифметика в 32 битах там, где произведение может превысить 2³² (ширина × высота × байт на пиксель, число точек × 2).
  3. inflate: расстояние назад больше уже распакованного; длина копии за пределом выхода; таблица Хаффмана из
     «невозможных» длин кодов (слишком много кодов одной длины); предел общего размера распакованных данных.
  4. png_unfilter: первая строка и первый пиксель (нет «верхнего» и «левого»), неизвестный тип фильтра, данных меньше,
     чем строк × (1 + ширина строки).
  5. Составные глифы: глиф, ссылающийся на себя или по кругу (A → B → A) — есть ли предел глубины; число компонент;
     индекс глифа больше `numGlyphs`.
  6. `static_cast` к меньшему или знаковому типу от значений из файла — на что-нибудь из перечисленного выше.
- **Что прислать.** Список «`файл:строка` — что не так — какой входной файл это вызовет» (можно коротко). Если всё чисто —
  так и напишите и какие пункты смотрели. Под каждое найденное я напишу испорченный файл-тест (он ляжет в набор
  регрессий и потом в фаззинг П.7) и исправлю.
- **Результат:** buildHuffman (строка 32): ++code.counts[lengths[symbol]]; — нет проверки lengths[symbol] < 16. Вызовет OOB-запись, если в buildHuffman передать массив lengths со значением >= 16.
 readBits (строка 17): 1u << need — при need >= 32 произойдёт UB (в текущем inflate need <= 13, но сама функция от need >= 32 не защищена).
 readComponent (строки 71–72): readOffset и readTransform сдвигают position, не проверяя position <= end глифа. На обрезанном составном глифе (numberOfContours < 0, 14 байт в loca, флаги HAS_TWO_BY_TWO | ARGS_ARE_WORDS) чтение выйдет за границу глифа и тихо завершится без ошибки.
 readComponent (строка 74): нет проверки glyph < glyphCount для вложенного компонента (она есть только для корневого глифа в FontFace::outline, строка 114). Составной глиф со ссылкой на glyphIndex >= maxp.numGlyphs прочитает чужую запись из loca.
 readSimpleGlyph (строка 89): cursor.position += 2 + reader.u16(cursor.position); — перед чтением длины инструкций нет проверки cursor.position + 2 <= cursor.end. На простом глифе, обрезанном сразу после endPtsOfContours (12 байт в loca), u16 прочитает 2 байта из следующего глифа в glyf.
 unfilter (строка 73): stride * header.height вычисляется в std::size_t. На 32-битной сборке (если MAX_SIDE >= 65536) при 65536 × 65536 RGBA произведение переполнит size_t и сможет совпасть с маленьким raw.size()
- **Разбор (2026-11-14):** все шесть замечаний верные, исправлено всё.
  1. `inflate_bits.cpp` `buildHuffman` — длина кода > 15 писала за `counts[16]`. Сейчас из файла такая длина не
     приходит (код длин даёт 0–15, длины кода длин — 3 бита), но функция доверяла вызывающему. Исправлено: проверка
     `lengths[i] > MAX_CODE_BITS` до записи → `false`; число 16 заменено константой во всех циклах.
  2. `readBits` — `1u << need` при `need ≥ 32` и переполнение 32-битного буфера при `need > 24`. Сейчас `need ≤ 13`.
     Исправлено: `need` вне 0..`MAX_READ_BITS` (24) → `failed` и 0.
  3. `font_composite.cpp` `readComponent` — смещение и матрица читались без проверки конца глифа: на обрезанном глифе
     читались байты следующего, и контур получался «правдоподобным». **Настоящая ошибка** (ASan её не видит: чтение
     внутри файла, `FontReader` ограничен файлом, а не глифом). Исправлено: размер записи считается по флагам
     (`componentRecordSize`) и сравнивается с остатком глифа до чтения; нехватка — весь составной глиф испорчен.
  4. `readComponent` — индекс вложенного глифа не сравнивался с `numGlyphs`: читалась чужая запись за таблицей loca.
     Исправлено: проверка `glyph < glyphCount` в `readGlyph` — для корня и для всех вложенных.
  5. `font_glyf.cpp` `readSimpleGlyph` — длина инструкций читалась без проверки `position + 2 ≤ end`. Исправлено:
     `skipInstructions` проверяет и длину, и сами инструкции по остатку глифа. Попутно `readContours` проверяет, что
     концы контуров помещаются в глиф, **до** их чтения (раньше — после).
  6. `png_unfilter.cpp` — `stride × height` в `size_t`. При нынешних пределах (16384 × 16384, 16 бит × 4 канала)
     произведение в 32 битах помещается, но проверка держалась на чужом пределе. Исправлено: произведение в 64 битах,
     и в `png_decoder.cpp` ожидаемый размер — в 64 битах с проверкой против `SIZE_MAX`.

  **Найдено мной при разборе (того же класса):** зацикленный составной глиф. Предел глубины 8 не спасает от ветвления:
  глиф из k компонент, каждая из которых ссылается на него же, — k⁸ вызовов (300 компонент — разбор не кончается).
  Добавлен общий предел посещённых глифов на контур (1024). Пункт 5 задачи (циклы) это и спрашивал — я его недооценил,
  проверив только глубину.

  **Что нашёл человек и чего не поймала автоматика:** все шесть. Модульные тесты брали только целые шрифты и PNG,
  ASan видит лишь выход за выделенную память (здесь — чтение внутри файла), clang-tidy аудита 2026-11-12 эти места
  не отметил. **Что добавлено в автоматику:** синтетические шрифты из байтов (`tests/support/font_samples.*`) и тесты
  `font damage: …` (обрезанный составной, ссылка за numGlyphs, обрезанный простой, самоссылка ×301 — быстрее 2 с),
  `inflate limits: …` (длина 16, переподписка, 24/25/32/−1 бит). Эти шрифты — готовые семена для фаззинга (П.7).
