## Номер версии

Грань UI нумеруется по [семантическому версионированию 2.0.0](https://semver.org/lang/ru/):
**МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ**, например `0.1.0`, `1.4.2`, `2.0.0-rc.1`.

| Часть | Когда растёт | Пример |
|---|---|---|
| МАЖОРНАЯ | Несовместимые изменения публичного интерфейса, разметки или Си-ABI | `1.4.2` → `2.0.0` |
| МИНОРНАЯ | Новые возможности без поломки совместимости | `1.4.2` → `1.5.0` |
| ПАТЧ | Только исправления ошибок | `1.4.2` → `1.4.3` |
| Суффикс | Предвыпуски: `-dev` (ветка main), `-rc.N` (кандидат перед выпуском) | `1.5.0-rc.1` |

Номер записан в одном месте — [`include/gran/gran_version.h`](../include/gran/gran_version.h).
Оттуда его берут CMake (`project(VERSION …)`), функции `gran_version_number` / `gran_version_string`
и тест `version string matches numbers`. Тег git (`vX.Y.Z`) и раздел в [CHANGELOG.md](../CHANGELOG.md) должны совпадать
с заголовком — это проверяется перед каждым выпуском.

Отдельно от версии движка ведётся **версия Си-ABI** — `GRAN_ABI_VERSION` (`gran_abi_version()`). Она растёт
только при несовместимом изменении двоичного интерфейса `gran.h`: удалена функция, изменена сигнатура,
раскладка структуры или значение перечисления. Новые функции ABI не меняют. Обёртки Python, C# и Java
при загрузке сверяют её и отказываются работать с чужой.

## Ветки

```
main ──●──●──●──●──●──●──●──●──●──●──●──►   разработка, версия 0.(N+1).0-dev
        \                \
         release/0.1      release/0.2       только исправления
          ●─v0.1.0─●─v0.1.1    ●─v0.2.0─●─v0.2.1
```

- **`main`** — разработка. Здесь появляются новые возможности, здесь же (и только здесь) допускаются
  несовместимые изменения. Номер в заголовке — следующая минорная версия с суффиксом `-dev`. Гарантия у `main`
  одна: каждый коммит собирается и проходит тесты на Windows и Linux.
- **`release/X.Y`** — ветка выпуска. Создаётся от `main`, когда минорная версия готова; на ней ставятся теги
  `vX.Y.0`, `vX.Y.1`, … На ветке действуют [гарантии](#гарантии-на-ветках-releasexy) ниже.
- Исправление делается сначала в `main` (если ошибка там есть), затем переносится `git cherry-pick -x` на
  поддерживаемые ветки `release/X.Y`. Изменение только для ветки выпуска — исключение и помечается в CHANGELOG.
- Ветки задач (`claude/…`, `feature/…`, `fix/…`) живут до слияния в `main` и после него удаляются.

## Гарантии на ветках release/X.Y

То же кратко записано в шапке [`include/gran/gran_export.h`](../include/gran/gran_export.h).
Если гарантия нарушена — это ошибка выпуска, и она исправляется следующим патчем.

1. **Двоичная совместимость Си-интерфейса.** Программа или обёртка, собранная с `gran_c` версии X.Y.0,
   работает с любой `gran_c` X.Y.Z без пересборки: достаточно заменить `gran_c.dll` / `libgran_c.so`.
   Функции не удаляются и не меняют сигнатуру, раскладка структур и значения перечислений и кодов
   `gran_status` не меняются, `GRAN_ABI_VERSION` не меняется. Новые функции в патч-выпуск не добавляются.
2. **Совместимость исходников C++.** Объявления в `include/gran/` (кроме папок `internal/`) не удаляются
   и не переименовываются, типы параметров не меняются. Поведение меняется только там, где оно было ошибкой,
   и такое изменение описывается в CHANGELOG. Двоичной совместимости C++ нет: `libgran` — статическая
   библиотека, после обновления программа пересобирается.
3. **Совместимость разметки.** Документ, проходящий схему `schemas/gran-ui.xsd` версии X.Y.0, проходит её
   и в X.Y.Z и строит то же дерево элементов. Не меняются форматы файлов настроек (`gran-settings.xsd`)
   и манифеста ресурсов (`gran-resources.xsd`), тема по умолчанию меняется только для исправления ошибок.
4. **Сообщения и коды ошибок.** Идентификаторы каталога сообщений и коды ошибок не удаляются и не меняют
   смысл (тексты сообщений могут уточняться).
5. **Требования не повышаются.** Минимальные версии на ветке не растут: Windows 10 1909, MinGW-w64 GCC 11 или
   MSVC 2022 на Windows, GCC 8 и glibc 2.27 на Linux (Astra Linux SE 1.7), Vulkan 1.0, Direct3D уровня функций 11_0.
6. **Состав патч-выпуска:** исправления ошибок, уязвимостей, сборки на новых версиях компиляторов и ОС,
   документации. Без новых возможностей и без рефакторинга «заодно».
7. **Каждый тег проверен:** `make test` на Windows и Linux, `make test-render` (D3D12, D3D11, Vulkan
   на программном устройстве), тесты обёрток, сборка через CMake.

## Что гарантиями не покрыто

- Всё в папках `include/gran/**/internal/` и `src/` — внутреннее устройство.
- Объявления с пометкой `GRAN_EXPERIMENTAL` — новые части, которые могут измениться в любой минорной версии.
- Попиксельное совпадение кадра между выпусками: исправление сглаживания или шрифта может сдвинуть пиксели
  (сравнение снимков — с допуском, см. [проверки отрисовки](render_testing.md)).
- Сгенерированные файлы (`src/rhi/shaders_gen/`, `gen/`), примеры (`examples/`, `samples/`) и инструменты разработки.
- Поведение, которое противоречит документации, — это ошибка, и её исправление не считается поломкой.

## Правила до версии 1.0

Пока мажорная версия `0`, движок молодой, и по SemVer минорная версия может содержать несовместимые изменения.
Чтобы этим можно было пользоваться, у Грани UI правила строже:

- Внутри ветки `release/0.Y` действуют **все** гарантии выше — патч-выпуски `0.Y.Z` безопасны.
- Между минорными версиями (`0.1` → `0.2`) C++ API и разметка **могут** меняться несовместимо, но каждое такое
  изменение перечислено в разделе «Несовместимые изменения» CHANGELOG с указанием, как обновить код.
- **Си-ABI ломается только с повышением `GRAN_ABI_VERSION`**, даже до 1.0. Обёртки увидят несовпадение сразу
  при загрузке библиотеки, а не падением посреди работы.
- Где возможно, старое сначала помечается `GRAN_DEPRECATED` и удаляется не раньше следующей минорной версии.

С версии **1.0.0** несовместимые изменения — только в мажорных версиях.

## Устаревание и удаление

1. Замена добавляется в `main`, старое объявление помечается `GRAN_DEPRECATED("используйте …")`
   (для атрибутов разметки — предупреждение в журнале при загрузке и пометка в документации).
2. В CHANGELOG — раздел «Устарело» с заменой.
3. Удаление — не раньше следующей минорной версии до 1.0 и не раньше следующей мажорной после 1.0;
   только в `main`, никогда на ветке выпуска.

## Проверка версии из программы

При компиляции — макросы заголовка:

```cpp
#include "gran/gran_version.h"

#if !GRAN_VERSION_AT_LEAST(0, 2, 0)
#error "Нужна Грань UI 0.2.0 или новее"
#endif
```

Во время работы (для обёрток и программ, которые подгружают `gran_c` как DLL):

```c
#include "gran/capi/gran.h"

if (gran_abi_version() != GRAN_ABI_VERSION) { /* библиотека несовместима */ }
printf("Грань UI %s\n", gran_version_string());   /* версия собранной DLL */
```

`GRAN_VERSION_NUMBER` и `gran_version_number()` кодируют версию числом `МАЖОР·1 000 000 + МИНОР·1000 + ПАТЧ`
(`1.2.3` → `1002003`), поэтому их можно сравнивать обычным `<`/`>`.

## Порядок выпуска

Выпуск — внешнее действие: тег и релиз публикует только владелец репозитория.

**Новая минорная версия X.Y.0**

1. В `main` завершены задачи версии из [плана работ](roadmap.md), открытых ошибок с пометкой «блокирует выпуск» нет.
2. Создать ветку `release/X.Y` от `main`; на ней в `gran_version.h` убрать суффикс `-dev` (`X.Y.0`).
3. В `CHANGELOG.md` и `CHANGELOG.en.md` раздел `[X.Y.0]` с датой: «Добавлено», «Изменено», «Несовместимые изменения»,
   «Устарело», «Исправлено».
4. Проверки из гарантии 7. При необходимости — кандидат `X.Y.0-rc.1` на неделю.
5. Коммит, тег `vX.Y.0` на ветке выпуска, отправка ветки и тега на GitHub и Gitverse.
6. В `main` поднять номер до `X.(Y+1).0-dev`.

**Патч-выпуск X.Y.Z**

1. Исправление влито в `main` и перенесено на `release/X.Y` (`git cherry-pick -x`).
2. `GRAN_VERSION_PATCH` + 1, раздел `[X.Y.Z]` в CHANGELOG (только «Исправлено» и «Безопасность»).
3. Проверки, тег `vX.Y.Z`, отправка на оба сервера.

## Поддержка выпусков

| Период | Какие ветки получают исправления |
|---|---|
| До 1.0 | Только последняя минорная ветка `release/0.Y` |
| После 1.0 | Две последние минорные ветки; исправления уязвимостей — также последней минорной ветке предыдущей мажорной версии в течение 12 месяцев после выхода новой мажорной |

Сроки выпусков и состав версий — в [плане работ](roadmap.md#выпуски). Об уязвимостях — [SECURITY.md](../SECURITY.md).
