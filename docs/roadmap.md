## Направление

Главная цель — **своя основа для настольных программ любой сложности под любой заказ**: Windows, Linux (включая
российские ОС — Astra Linux, Альт, РЕД ОС) и macOS, программы пишутся на C++ или через обёртки Python, C#, Java. Вторая линия — интерфейс внутри игр на том же ядре. Повторять всё, что есть в Qt, цели нет:
движок растёт от задач реальных программ.

Правила для каждого пункта плана:

- работает на Windows **и** Linux; новое проверяется модульными тестами и снимками кадра;
- новые элементы и атрибуты сразу попадают в схему `gran-ui.xsd`, доступность (UI Automation) и Си-интерфейс
  с обёртками Python, C#, Java;
- документация RU и EN обновляется в том же изменении;
- сквозная идея — использовать «Берёсту» не только при загрузке: живой DOM, XPath (привязки, запросы, тесты),
  XSD (проверка разметки, типы полей ввода, правила дизайна через `xs:assert`), SAX (большие данные),
  XInclude (сборка из файлов).

Этап 1 «Фундамент программ» завершён (события, команды, отмена, живой документ, выражения привязки, компоненты,
модели данных, окна и программа) — он входит в версию 0.1.0.

## Первый приоритет: macOS без своего Mac

Решение 2026-11-12: подготовка к macOS — **первый приоритет**, раньше пунктов этапа 2. Своего Mac пока нет (покупка —
позже), но большую часть работы можно сделать и проверить уже сейчас: репозиторий публичный, а для публичных
репозиториев стандартные раннеры GitHub Actions, в том числе macOS на Apple Silicon, бесплатны. Прежняя оговорка про
дорогие минуты macOS (множитель для закрытого репозитория) больше не действует.

| Шаг | Что | Чем проверяется без Mac |
|---|---|---|
| **M1** ✓ | Сделано 2026-11-13 ([архитектура](architecture.md#контракт-платформы-platform)): контракт `platform::` (окно, цикл событий, клавиши `Mod` = Ctrl/Cmd, IME, буфер обмена, курсоры, дробный масштаб, точная прокрутка) в документации архитектуры; поиск «утечек» Win32/X11 в общем коде | ревью кода, сборка Windows/Linux |
| **M2** | Безоконная платформа для тестов (события из теста, кадр — из памяти), Р.1 и С.2 | `make test` на Windows и Linux |
| **M3** | Сборка ядра на macOS (clang, Makefile и CMake), модульные тесты с безоконной платформой; workflow `macos.yml` на каждый push | раннер macOS в CI |
| **M4** | Шейдеры для Metal: тот же HLSL → dxc → SPIR-V → MSL (SPIRV-Cross при сборке, как dxc — инструмент, не зависимость движка), сгенерированные массивы, проверка `xcrun metal` | компиляция шейдеров на раннере |
| **M5** | Бэкенд Metal вне экрана (`src/rhi/metal/`): устройство, буферы, текстуры, проход отрисовки, чтение кадра; снимки против эталонов с допуском | сборка всегда; снимки — только если на раннере есть устройство Metal (первым делом — проба `MTLCreateSystemDefaultDevice` в CI: у раннеров Apple Silicon GPU может не быть) |
| **M6** | Платформа Cocoa (`src/platform/cocoa/*.mm`): окно с CAMetalLayer, Retina, ввод, буфер обмена, курсоры | сборка и тест в процессе (`[NSApp postEvent:]`, кадр — своим чтением) на раннере |

Без Mac не проверить — это задачи на покупку Mac или аренду облачного Mac на контрольные точки: трекпад и инерция,
IME (CJK, мёртвые клавиши), VoiceOver, вид шрифтов на Retina, подпись и нотаризация `.app`. MoltenVK не берём: это
сторонняя библиотека (правило «без зависимостей»), и на раннере без GPU она живой кадр тоже не даст.

## Готовность к промышленному использованию

Рекомендации, без которых движок трудно ставить в серьёзные программы. Номера П.N используются в таблице выпусков.

**П.1. Непрерывная проверка (CI).** Сейчас проверки запускаются вручную. Нужно: workflow GitHub Actions и Gitverse
на каждый коммит в `main`, `release/*` и запрос на слияние — Windows (MinGW + make, MSVC + CMake), Linux
(GCC 8 в образе Astra Linux SE 1.7 — самый старый целевой glibc; свежие GCC и Clang), `make test`,
`make test-render` на WARP и lavapipe, тесты обёрток Python/C#/Java; предупреждения компилятора в CI — ошибка.
Готово, когда ветку нельзя влить с красной проверкой.

**П.2. Сборка выпуска по тегу.** Тег `vX.Y.Z` запускает сборку архивов: Windows x64 (MinGW и MSVC), Linux
x86_64 (сборка в Astra 1.7, работает на более новых дистрибутивах), заголовки, `libgran.a`, `gran_c`,
инструменты (`gran_rcc`, `gran_snapshot`), контрольные суммы SHA-256 и описание из CHANGELOG. Позже — aarch64.

**П.3. Проверка двоичного интерфейса.** Для каждой публичной структуры `gran.h` — `static_assert` на `sizeof`
и `offsetof` полей (как уже сделано для структур видеокарты). Свой скрипт сравнивает список экспортируемых символов
`gran_c` и сигнатуры в `gran.h` с тегом `vX.Y.0`; на ветке `release/X.Y` любое отличие — провал CI.

**П.4. Проверка совместимости разметки.** Корпус разметки (примеры `samples/`, фрагменты документации, тесты)
версии X.Y.0 обязан проходить схему ветки выпуска. Сравнение схем: на ветке допустимы только исправления,
в минорной версии — только расширения (новые элементы и необязательные атрибуты).

**П.5. Пакет для подключения.** `cmake --install` раскладывает заголовки, библиотеки и `GranUIConfig.cmake`
с `GranUIConfigVersion.cmake` (совместимость `SameMinorVersion` до 1.0, `SameMajorVersion` после), чтобы
программа писала `find_package(GranUI 0.3 CONFIG REQUIRED)`; файл `gran-ui.pc` для pkg-config; у Linux-библиотеки
`libgran_c.so.<ABI>` правильное имя soname; у `gran_c.dll` и программ-примеров — ресурс VERSIONINFO с номером
из `gran_version.h`, значок и манифест. Сборка проверяет минимальную версию «Берёсты».

**П.6. Версия в обёртках.** Python `granui.__version__`, C# `AssemblyVersion`, Java `Implementation-Version` берут
номер из `gran_version.h`; при загрузке обёртка сверяет `gran_abi_version()` (уже есть) и предупреждает в журнал,
если минорная версия DLL отличается от её собственной.

**П.7. Санитайзеры и фаззинг** (сквозная задача С.4). До 1.0 обязательно: ночной прогон тестов с ASan и UBSan,
TSan на пуле задач, `post` и потоковых источниках данных; фаззеры для разметки, стилей, PNG, JPEG, SVG, шрифтов
TrueType и JSON; найденные входы — в набор тестов.

**П.8. Статический анализ.** *Начато 2026-11-12:* `.clang-tidy` в репозитории, первый прогон разобран (ошибки
исправлены, находок clang-analyzer — 0; остаток — шум и намеренные места, журнал). Осталось: CI, MSVC `/analyze`, cppcheck.
clang-tidy (группы bugprone, cert, performance, concurrency), MSVC `/analyze`,
cppcheck — в CI, без накопленного «долга»: новое предупреждение — провал.

**П.9. Безопасность цепочки поставки.** Подписанные теги (`git tag -s`), SHA-256 и подпись архивов выпуска,
SBOM в формате CycloneDX (движок, «Берёста», системные библиотеки), подпись Authenticode для exe и dll на Windows,
таблица поддерживаемых версий и сроков ответа на сообщения об уязвимостях в [SECURITY.md](../SECURITY.md).

**П.10. Документация для обновления.** В каждой минорной версии — раздел «Как обновиться с 0.X на 0.Y» с примерами
до/после; справочник API, собранный своим генератором из двуязычных комментариев заголовков; документация на сайте
с переключателем версий.

**П.11. Производительность как регрессия** (сквозная задача С.5). Замеры старта, памяти, времени кадра и размера
программы на эталонных разметках в CI; ухудшение больше чем на 10 % без объяснения — провал.

**П.12. Проверка на железе и ОС.** Перед каждой минорной версией — видеокарты AMD, NVIDIA и встроенная Intel;
ОС — Windows 10 22H2, Windows 11, Astra Linux SE 1.7 и 1.8, Альт p10 и p11, РЕД ОС 7.3 и 8, Ubuntu LTS.
Результат — таблица в описании выпуска.

**П.13. Контракты потоков и времени жизни.** У каждого публичного класса и функции в заголовке записано: из какого
потока вызывать, кто владеет объектом, что делает ссылки недействительными. Проверки потока, которые уже есть
в Си-интерфейсе, распространяются на `gran::Application` в отладочной сборке.

**П.14. Наблюдаемость.** Уровень журнала из переменной окружения и настроек; в начале журнала — версия движка, ABI,
«Берёсты», ОС, видеокарта и выбранный бэкенд (часть уже пишется), чтобы отчёт о сбое сразу говорил, на чём он случился.

**П.15. Версия схемы разметки.** Схема каждой минорной версии публикуется по постоянному адресу, а разметка может
указать нужную версию (атрибут или пространство имён) — тогда редактор проверяет её схемой той версии движка,
под которую она написана, а движок предупреждает о разметке из более новой версии.

**П.16. Контур качества для кода, написанного с ИИ.** Большая часть кода движка пишется языковыми моделями под контролем
человека, а ошибки в шейдерах, буферах GPU и ручной работе с памятью не падают сразу — они портят кадр или память
через минуты. Поэтому у каждой большой доработки три уровня проверки:
1. **Автоматические:** модульные тесты и снимки кадра; сборка с санитайзерами — `make DEBUG=1 SANITIZE=address,undefined test`
   на Linux (GCC/Clang), CMake `-DGRAN_SANITIZE=address` с MSVC на Windows (сделано в 0.1.0); TSan для кода с потоками;
   Valgrind memcheck для своих парсеров; отладочные слои D3D12 (с GPU-Based Validation) и Vulkan (с synchronization
   validation) при прогоне снимков — любое сообщение слоя считается ошибкой.
2. **Правила для шейдеров и структур GPU:** dxc с `-Wall -WX`, проверка SPIR-V `spirv-val`, `static_assert` на размер
   и смещения каждой структуры, общей для C++ и HLSL, ограничение индексов в шейдере в отладочной сборке.
3. **Человек в контуре:** после каждой большой доработки готовятся подробные задачи ручной проверки
   ([tests/manual](../tests/manual/README.md)): живое окно, вид кадра, захват кадра в RenderDoc или PIX, проверка
   в отладчике, долгие сессии, реальные видеокарты и рабочие столы Linux. В разборе каждой задачи отмечается, что
   нашёл человек и чего не поймала автоматика, — и это превращается в новую автоматическую проверку.

В CI (П.1) этот набор запускается на каждый коммит: санитайзеры — на Linux, отладочные слои — на WARP и lavapipe.

## Архитектурные риски

Зоны, где движок может «упереться» при росте, и что делаем заранее, чтобы не переписывать потом.
Раздел составлен по рекомендациям ведущего разработчика проекта (2026-11-04).

### Р.1 Переносимость платформы (готовимся к macOS заранее)

**Сейчас:** Windows 10/11 (Win32) и Linux (X11/XWayland). **Риск:** перенос на macOS потребует новой абстракции окон,
ввода и клавиатуры; если интерфейс `platform::` невольно повторяет Win32 или X11, порт превратится в переделку.
**Что делаем:**
- описать контракт `platform::` (окно, цикл событий, клавиши, текстовый ввод, буфер обмена, курсоры, DPI) в документации
  архитектуры и проверить его на «утечки» конкретной ОС: коды клавиш физические и логические, модификатор `Mod`
  (Ctrl на Windows/Linux, Cmd на macOS), протокол IME (составляемая строка, позиция окна кандидатов), точная прокрутка
  трекпадом, дробный масштаб;
- сделать третью реализацию — «безоконную» платформу для тестов (события подаются из теста, кадр читается из памяти):
  она и ускоряет тесты интерфейса (С.2), и сразу показывает, где абстракция держится за Win32/X11;
- **когда:** контракт и безоконная платформа — первый приоритет (шаги M1–M2 раздела «Первый приоритет»); порт — шаги M3–M6 там же.

### Р.2 Видеопамять и долгие сессии

**Сейчас:** D3D12, D3D11, Vulkan, программные WARP и lavapipe. **Риск:** переход между бэкендами (запасной путь
D3D12 → D3D11, потеря устройства, смена видеокарты) требует согласованно пересоздать конвейеры, кэши текстур и атлас;
на сессиях в часы и дни возможны рост и фрагментация видеопамяти (атлас глифов, таблица текстур, буферы картинок).
**Что делаем:**
- учёт видеопамяти: бюджет и занятость через `IDXGIAdapter3::QueryVideoMemoryInfo` и `VK_EXT_memory_budget`, счётчики
  движка (атлас, текстуры, буферы загрузки) — в журнал и в инспектор (С.1);
- выделение крупными блоками с подраспределением внутри (вместо отдельного выделения на каждый ресурс), повторное
  использование освобождённых областей, уплотнение атласа глифов при фрагментации выше порога;
- проверка пересоздания: тест, который принудительно «теряет» устройство (D3D12 `RemoveDevice`, переключение
  бэкенда на лету) и сравнивает кадр до и после — сцена хранится на процессоре, поэтому кадр должен совпасть;
- «долгий прогон»: окно с анимациями, прокруткой и сменой картинок 8–24 часа с записью памяти процесса и видеопамяти
  раз в минуту; рост больше заданного порога — ошибка; ручная задача на реальных видеокартах;
- **когда:** учёт памяти и тест потери устройства — 0.3–0.5; подраспределение и уплотнение — до 1.0.

### Р.3 Текст: CJK, возможности OpenType, письмо справа налево

**Сейчас:** свой разбор TrueType, атлас на GPU, кернинг, замена шрифта для CJK. **Риск:** тексты CJK (тысячи разных
глифов), возможности OpenType (лигатуры, вариативные шрифты) и письмо справа налево потребуют расширить движок
формирования текста; если модель текста рассчитана на «один символ — один глиф слева направо», это переписывание.
**Что делаем:**
- уже сейчас держать модель текста готовой к росту: кластеры (несколько символов ↔ несколько глифов), логический
  и визуальный порядок раздельно, каретка и выделение — по кластерам; тесты на это без сложных письменностей
  (лигатуры латиницы, комбинируемые диакритики);
- атлас из нескольких страниц с вытеснением редко используемых глифов — для CJK (вместе с Р.2);
- GSUB (лигатуры), вариативные шрифты, цветные эмодзи — пункт 3.1;
- алгоритм двунаправленного текста Unicode (UAX #9) и зеркальная компоновка — остаются в «Отложено», но интерфейсы
  формирования текста проектируются так, чтобы их можно было добавить без смены публичного API;
- **когда:** модель кластеров и многостраничный атлас — до 1.0; остальное — 3.1 и по запросу.

### Р.4 Код, сгенерированный языковыми моделями

**Сейчас:** проверка человеком, модульные тесты, снимки кадра. **Риск:** шейдеры и работа с буферами GPU, написанные
моделью, могут выглядеть правильно и проходить тесты, но читать за границами буфера, гоняться за данными между
CPU и GPU или течь. **Что делаем:** контур качества П.16 — санитайзеры, Valgrind, отладочные слои GPU, RenderDoc и PIX,
правила для шейдеров и задачи ручной проверки; правила кода для моделей (`gpu_rules`) обновляются по каждой
найденной ошибке. **Когда:** сборка с санитайзерами и ручные задачи — с 0.1.0; всё в CI — с 0.2.0.

### Р.5 Встроенный браузер на Linux

**Сейчас:** `<WebView>` работает только на Windows (WebView2); на Linux это пустой блок. **Риск:** программы, которым
нужен веб-контент, на Linux получают дыру в интерфейсе. **Варианты:**
1. **WebKitGTK через `dlopen`** (как уже сделано с Vulkan): без зависимости при сборке, есть в репозиториях Astra, Альт
   и РЕД ОС, веб-процесс отдельный. Сложность — встроить окно GTK в окно X11 движка и совместить циклы событий.
2. **Встроенный Chromium (CEF):** одинаковое поведение везде, но +100–200 МБ к поставке и своё обновление безопасности.
3. **Оставить WebView только для Windows:** честно документировать, а на других ОС показывать запасное содержимое.
**Рекомендация:** сразу — вариант 3 как обязательная основа: дочернее содержимое `<WebView>` показывается, когда
браузера нет, и переменная `$webViewAvailable` для разметки; затем — вариант 1 для Linux, если появится программа,
которой это нужно. CEF — только по прямому запросу. **Когда:** запасное содержимое — 0.4; WebKitGTK — этап 3 или 4.

## Доработки сделанного

Небольшие хвосты готовых частей. Берутся попутно с пунктами этапов, если касаются той же области.

**Команды и клавиши.** Системные (вне программы) горячие клавиши; клавиши знаков `+`, `-`, `/` в сочетаниях;
команды с отметкой (checked); `enabled="{…}"` у `<Command>`.

**Отмена и повтор.** Макрошаги (`beginMacro`/`endMacro`) — общий шаг отмены для группы действий; отмена в UI Automation;
API заголовка окна (звёздочка несохранённого документа).

**Живой документ.** Правка атрибутов `<Window>` и `<Resources>` (стилей, темы) через живой DOM без полной
перезагрузки; вставка и перестановка элементов через DOM; при вставке ребёнка перестраивать не весь родитель,
а сопоставлять узлы по `id`.

**Выражения привязки.** Выражения в `Style` и состояниях; новые `<Variable>` при частичной перезагрузке; поиск
копии записи без линейного прохода (сейчас O(n) на привязку); свойства узлов (`$id.свойство`) в фильтрах представлений.

**Компоненты.** Параметры в `style` и перечислениях; компоненты, объявленные прямо в окне; `xpointer`
и `xi:include` внутри библиотек.

**Модели.** UI Automation для списков с выделением; ленивые деревья из файлов (сейчас дерево читается целиком).

**Окна и программа.** Своя XSD программы для значений её настроек; `<WebView>` с содержимым из `res:/`;
перехват переполнения стека в потоках пула задач (Linux); центрирование окон с учётом нескольких мониторов в X11.

**Текст.** Строки разной высоты внутри одного блока (участок с большим кеглем); разбор Markdown только изменившегося
хвоста при потоковом выводе.

**Списки и компоновка.** Виртуализация `Grid`; обход детей очень длинного невиртуального стека без O(n) на каждый проход.

**Каркас окна.** Прокрутка полосы вкладок стрелками (сейчас переполнение — меню); длина края дока и положение
разделителя с клавиатуры у ручки края; сохранение оторванных панелей между запусками; буквы доступа у кнопок и подписей
полей (сейчас — только меню); события UI Automation о раскрытии и свёртывании меню; панели одного края дока рядом
(сейчас — только вкладками).

**Всплывающие слои.** Задержка закрытия подменю при движении мыши
наискосок; ширина ComboBox по самому длинному пункту; подпись ComboBox при правке модели списка.

**Виджеты и анимации.** `animationPlayState` и пауза; перезапуск анимации из кода; смешивание
преобразований разной формы через матрицы (сейчас — скачок); анимации в `gran_snapshot` на заданный момент времени.

**Доступность.** ScrollPattern у Scroll, TextPattern (каретка и выделение для экранных дикторов), LiveRegion
(объявления о смене текста не в фокусе, например статуса), события смены значения у узла не в фокусе,
LabeledBy как свойство UIA.

**Картинки.** Быстрое обратное DCT у JPEG; чересстрочные PNG (Adam7).

**Разработка.** Перезагрузка отдельных ассетов (картинок, шрифтов) без перезагрузки разметки; применение
параметров окна ОС при перезагрузке.

**Linux.** Передача больших данных буфера обмена (INCR); браузер для `<WebView>`.

- macOS (подробный план — в [идеях](#macos)), Android, iOS, WebAssembly;
- 3D, видео, Lottie, MathML; решатель ограничений, subgrid;
- AT-SPI и собственный Wayland (на российских ОС основной сервер — X11);

- сенсорный ввод, перо и жесты; автообновление программ; проверка орфографии и переносы по словарям.

## Идеи на будущее

Идеи обсуждены, но ещё не стали пунктами плана. Их содержание может сильно измениться.

### Интерфейс, настраиваемый пользователем

Конечный пользователь программы не правит XML. Кнопка или сочетание клавиш переводит окно в режим правки, и прямо
в нём можно перетаскивать и добавлять кнопки, панели и другие части, объединять и разделять их функции в пределах
того, что программа разрешила. Пример для редактора кода: собрать несколько действий с файлом в одну кнопку или
добавить боковую панель ещё для одного ассистента.

Это реально, потому что интерфейс Грани UI — декларативные данные, проверяемые схемой. Строится из готовых частей:

1. **Режим правки** — слой поверх окна: рамки выделения, ручки, зоны вставки (перетаскивание узлов и hit-test уже есть).
2. **Палитра** — только то, что программа разрешила: зарегистрированные `<Command>` и шаблоны панелей-компонентов
   (например, «панель ассистента» с параметром «модель»). Добавить то, чего программа не умеет, нельзя.
3. **Составная кнопка** — список команд, выполняемых по порядку (без скриптов), с общим шагом отмены.
4. **Изменения** — правка живого DOM с проверкой XSD и откатом, отмена и повтор правок раскладки.
5. **Сохранение** — не копия интерфейса, а наложение-патч поверх базовой разметки по стабильным `id`: обновление
   программы не затирает настройки, неизвестные `id` пропускаются с предупреждением; хранится в каталоге настроек
   пользователя.
6. **Безопасность** — в пользовательском файле только раскладка, параметры и ссылки на зарегистрированные команды
   и шаблоны. Разработчик программы задаёт границы: какие области можно править (атрибут вроде `customizable`)
   и что есть в палитре.

Место в плане — вместе с закрепляемыми панелями (2.1) или отдельным пунктом после этапа 2.

### macOS

Шаги, которые делаются без Mac (M1–M6), — в разделе [«Первый приоритет»](#первый-приоритет-macos-без-своего-mac); здесь — полный план.

- **Графика** — свой бэкенд Metal (`src/rhi/metal/`), а не MoltenVK: Metal есть на всех поддерживаемых Mac,
  сторонняя библиотека не нужна. Шейдеры — тот же HLSL: dxc → SPIR-V → MSL через SPIRV-Cross при сборке.
- **Платформа** — Objective-C++ только в `src/platform/cocoa/*.mm`; публичные заголовки остаются чистым C++.
- **Шаги:** ядро и тесты без окна (CI на macOS) → Metal вне экрана и снимки против эталонов с допуском → окно
  Cocoa с CAMetalLayer и Retina → ввод (трекпад, IME, Cmd вместо Ctrl) → шрифты системы → диалоги файлов,
  своя рамка, меню программы → доступность NSAccessibility → universal binary, `.app`, подпись и нотаризация.
- **Проверка без своего Mac:** раннеры macOS в CI для сборки, тестов и снимков; аренда Mac на контрольные
  точки для живой проверки трекпада, IME, VoiceOver и вида шрифтов.

### Преобразование разметки в HTML

Отдельная утилита `tools/convert` (не в ядре): XML Грани UI → HTML + CSS — Stack и Grid в flex и grid, стили —
в классы CSS, состояния — в `:hover`/`:focus`. Нужна для предпросмотра в браузере и веб-версий программ и снимает
опасение «привязки» к движку.
