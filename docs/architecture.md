# Грань UI — архитектура движка

**Русский** · [English](architecture.en.md)

← [К описанию](../README.md)

Декларативный UI на XML поверх «Берёсты». Цель — качество картинки уровня HTML + CSS при старте за
миллисекунды, единицах МБ памяти и 0 % CPU в простое. Только C++17, стандартная библиотека и системные SDK
(Windows SDK для D3D12, Vulkan SDK для Vulkan, Xlib на Linux).

## 1. Конвейер

```
 XML-разметка ──► Берёста: разбор + XSD 1.1 (xs:assert, xs:key/keyref) за один проход
        │             ошибки: строка, столбец, путь /Window/Stack[2]/Button
        ▼
 markup/   DOM → дерево узлов UI (ui::Node), ресурсы (Theme, Style, Font, Image)
        ▼
 style/    каскад: умолчания ← тема ← Style ← атрибуты ← состояния (hover/pressed/focus/disabled)
        │   → ComputedStyle (POD) + переходы и ключевые кадры (animation/)
        ▼
 layout/   Stack (подмножество flexbox), Grid (px/auto/fr/minmax, span), Canvas (абсолютно),
        │   текст (text/: шрифт TrueType, кернинг, перенос строк) → LayoutBox (x, y, w, h)
        ▼
 render/   список отрисовки → экземпляры GpuInstance (прямоугольник SDF, тень, глиф, картинка,
        │   размытие подложки) + таблица отсечений + атлас глифов + рампы градиентов
        ▼
 rhi/      D3D12 | D3D11 | Vulkan | Null (запись для тестов): один instanced-вызов на сегмент,
           сегмент меняется только на проходе размытия подложки (glassmorphism)
```

Сохранённый режим (retained): каждый этап пересчитывается только по флагам «грязно»
(`STYLE_DIRTY` → `LAYOUT_DIRTY` → `PAINT_DIRTY`). Нет изменений и анимаций — нет кадра, поток спит в ожидании
событий ОС.

## 2. Модули (include/ и src/ зеркальны)

| `utils/` | UTF-8, разбор чисел и списков, геометрия (`Vec2`, `Rect`, `Affine2D`), цвет |

| `data/` | общий интерфейс списка `ListSource` (наблюдатель: вставка, удаление, правка диапазонов, перемещение, пересортировка) и его реализации: хранилище `ListModel` (записи-строки, столбцы таблицы, подгрузчик `ListFetcher`), прокси `SortFilterProxy` (порядок номеров источника, точечные правки), плоское дерево `TreeList`; дерево `TreeModel` со стабильными `NodeId` и ленивыми узлами; `SelectionModel` (отметки следуют за записями); сравнение `record_order` (текст без регистра, числа, natural); источники: свой читатель JSON `JsonReader` (вытягивание, порции) и XML через SAX «Берёсты» (путь select на лету, DOM только записи, ленивая подгрузка рабочим потоком с передачей из рук в руки); подстановка `{поле}`, переменные `Variable` |

| `layout/` | Stack, Grid, Canvas, измерение текста, прокрутка |
| `text/` | разбор TrueType/TTC, растеризация глифов (точная площадь покрытия), атлас, кернинг, перенос |
| `image/` | inflate (zlib), PNG и JPEG (baseline и progressive) — свои; формат — по подписи (`decodeImage`) |
| `vector/` | векторные фигуры иконок: разбор пути SVG (с дугами), файлы `.svg` через «Берёсту», растр точной площадью (nonzero/evenodd) |
| `animation/` | переходы свойств и анимации по ключевым кадрам (`<Keyframes>` + `animation`), кривые (`cubic-bezier`, ease, linear, steps), часы кадра |
| `undo/` | стек отмены (как `QUndoStack`): шаги `UndoStep` с объединением, позиция, «чистое» состояние, предел; им пользуются поля ввода и стеки приложения |
| `input/` | попадание (hit-test с учётом transform), фокус, маршрут событий, правка и выделение текста, буфер обмена, история правок полей (Ctrl+Z/Ctrl+Y) |
| `a11y/` | доступность: роли, имена, шаблоны управления, навигация по дереву, очередь запросов клиентов (нейтрально); провайдер UI Automation — в `platform/win32/uia_*`, запросы выполняет `InputRouter::perform` |
| `render/` | список отрисовки, упаковка экземпляров, отсечения, сегменты, кэш глифов |
| `rhi/` | интерфейс бэкенда, `null/`, `dx12/`, `vulkan/`, сгенерированные шейдеры `shaders_gen/` |
| `platform/` | окно и события: `win32/`, `x11/` (затем `cocoa/`); встроенный браузер `webview2/` (по желанию) |
| `app/` | приложение: окна (`AppWindow` на окно — документ, рендерер, ввод; общее — в `Application::State`; владелец — невладеющая ссылка на окно, стоящее в списке раньше: подчинённые закрываются раньше владельцев, графика уходит с конца списка; модальность — флаг `blocked` у владельцев, ввод отбрасывается до дерева, на Win32 ещё и `EnableWindow`), пул фоновых задач `TaskPool` (общая очередь, потоки при первой задаче, итог и слитый прогресс — через `post`), цикл событий, диалоги файлов, перетаскивание файлов, таймеры (`setTimeout`/`setInterval`), привязка действий (`onClick="имя"` → функция C++), размещение `<WebView>` |

### Встроенный браузер (гибрид)

Движок рисует интерфейс сам и браузер для этого не использует. `<WebView>` — единственное место, где появляется
веб-содержимое; его показывает браузер системы через интерфейс `platform::WebView` (паттерн Bridge):

- `platform/webview2/` — Windows, WebView2. Собирается только с SDK (`WEBVIEW2_SDK`); иначе
  `platform/web_view_fallback.cpp` возвращает `nullptr`, и элемент остаётся подложкой.
- Загрузчик `WebView2Loader.dll` подключается через `LoadLibraryEx` (каталог программы и System32) при первом
  показе элемента; COM — однопоточный апартамент потока окна.
- Создание асинхронное: колбэки COM (`ComCallback`, без лямбд) держат на ядро слабую ссылку, поэтому закрытие
  во время создания безопасно; команды до готовности копятся.
- После каждого кадра `app::syncWebViews` обходит видимые узлы, считает блок содержимого в физических пикселях
  и видимую часть (отсечение `Scroll`/`overflow`), создаёт браузер при первом показе и передаёт только изменения.
  Видимую часть задаёт дочернее окно-рамка, страница внутри него сдвинута на невидимую часть.
- Сообщения страницы складываются в очередь и обрабатываются после событий окна (`deliverWebMessages`),
  а не внутри колбэка браузера.
- Сейчас страница — дочернее окно поверх кадра движка. Следующий шаг — режим композиции
  (`ICoreWebView2CompositionController` + DirectComposition): страница станет визуалом между слоями движка,
  появятся всплывающие слои над ней, скругление и прозрачность; ввод тогда пересылает движок.
- Linux использует `web_view_fallback.cpp` без дополнительных браузерных зависимостей; macOS отложен.

## 3. Разметка и схема

- Корень — `<Window>`; ресурсы — `<Resources>`: `<Theme>` (именованные цвета и размеры), `<Style name=…>`
  с вложенными состояниями `<Hover>`, `<Pressed>`, `<Focused>`, `<Disabled>`.
- Элементы v1: `Stack`, `Grid`, `Canvas`, `Box`, `Text`, `Image`, `Button`, `Input`, `Scroll`; позже добавлены
  `CheckBox`, `Slider`, `TextArea` (многострочное поле: `rows`, `submitKey="ctrlEnter|enter"`, рост до `maxHeight`
  и своя прокрутка), `Span` (участок оформленного текста внутри `Text`: свой шрифт, цвет, `background`,
  `textDecoration`, ссылка `onClick`), `Popup` (всплывающий слой: скрыт до `Application::showPopup`, вне потока,
  поверх всего; Esc и щелчок мимо закрывают) и `MenuItem` (пункт меню в `Popup`). Атрибут `tooltip` у любого
  элемента — подсказка через 0,6 с; правый щелчок по тексту и полям — встроенное контекстное меню.
- Команды `<Command id text action key scope within enabled>` в `<Resources>` (паттерн Command, как QAction):
  `Button` и `MenuItem` ссылаются на них атрибутом `command`; загрузчик сразу даёт элементам подпись,
  подпись сочетания и enabled (`ui::bindCommandTree`), приложение — включённость из кода и глобальные команды
  других окон. Горячие клавиши ищет `input::matchCommand` по областям: focus (внутри `within`) → window → global.
- Имена атрибутов — camelCase и одинаковые у всех элементов (`gridRow`, `borderRadius`, `justify`, `align`).
  Отличия от черновика концепции: `grid-row` → `gridRow`; `alignment`/`verticalAlignment` →
  `justify` (главная ось) и `align` (поперечная ось) — не зависят от ориентации и не путаются.
- Схема XSD 1.1 встроена в библиотеку и проверяет документ **во время разбора** (`ParserOptions::schema`):
  - простые типы с шаблонами: цвет (`#rgb`, `#rrggbbaa`, `rgb()`, `hsl()`, `$имяТемы`), длина, список дорожек Grid;
  - `xs:assert` на ограничения интерфейса: `minWidth ≤ maxWidth`, номер строки/столбца Grid меньше числа дорожек,
    у `Button` есть текст или содержимое, `Scroll` содержит ровно один элемент и т. п.;
  - `xs:unique` на `id` в окне, `xs:key`/`xs:keyref` — ссылки `style="…"` только на объявленные стили.
  Ошибка — с позицией и путём ещё до создания окна.
- **Живой документ.** DOM «Берёсты» после построения не выбрасывается: `UiDocument::dom` (`shared_ptr`, чтобы
  публичный заголовок обходился объявлением `beresta::Document`), узел знает свой элемент невладеющей константной
  ссылкой `ui::Node::domElement` (менять элемент можно только через `internal::editableElement`). Узлы, которых нет
  в разметке (из кода, копии записей списков, полоса Tabs, слой ComboBox, подсказка и контекстное меню окна), ссылки
  не имеют. Инвариант: ссылка действительна, пока узел в дереве окна, — `remove` убирает элемент вместе с узлом
  (`detachMarkup`), `appendMarkup` переносит элемент фрагмента в DOM родителя (`keepFragment`).
  - Правка атрибута: запись в DOM → проверка всего DOM схемой (`xsd::SchemaValidator`) → построение поддерева
    из элемента; любая ошибка откатывает атрибуты. Приложение заменяет узел **на месте** (`app::rebuildInPlace`):
    узел остаётся тем же объектом (родитель, слушатели, наведение, фокус), его содержимое и потомки — новые;
    дети, добавленные во время работы (`markup::isRuntimeChild`), переносятся как есть.
  - Состояние пользователя (`ui/node_state.hpp`): текст полей с кареткой и историей, отметки, значения,
    выбор ComboBox/Tabs, прокрутка и фокус снимаются по ключам `#id` или «ключ предка/номер» и возвращаются
    узлам того же вида — при перестройке узла и при любой перезагрузке.
  - Частичная перезагрузка (`markup::planPatch` → `app::patchDocument`): новый документ строится целиком (проверка
    и откат как раньше); если `<Window>` и `<Resources>` равны, его DOM сравнивается с живым: равное поддерево
    (`isEqualNode`) остаётся, у узла с той же «оболочкой» (имя, атрибуты, свой текст, состояния, шаблон) и теми же
    детьми сравниваются дети, иначе узел перестраивается на месте из нового элемента со стилями живого документа.
    Ветви сначала все строятся, потом применяются. Различие пролога — полная замена с переносом состояния.
  - Сохранение: `serializeMarkup` — сериализатор «Берёсты» с отступами (пробельные отступы парсер не хранит,
    смешанное содержимое пишется в строку, комментарии сохраняются).
- **Выражения привязки** (`binding/expression_*`, паттерн Observer + вытягивающий пересчёт). Построитель узла
  только узнаёт `{…}` и проверяет синтаксис компиляцией XPath (ошибка — с позицией); узел хранит исходный текст
  (`ui::AttributeBinding`), а компиляция и вычисление — в модуле `binding/`: у `ui/` нет зависимости от XPath.
  - Данные для XPath — `DataMirror`: документ «Берёсты» `<data><модель><Item поле="…"/>…</модель></data>`; запись
    зеркала (`MirrorEntry`) — наблюдатель модели, правка меняет один элемент `Item` и номер версии модели.
  - Зависимости собирает свой сканер выражения: `$имя` (переменная), `$узел.свойство` (`self`, `parent`, id в окне
    привязки), `$index`, имена шагов пути (возможные модели), модель своей записи (при вычислении). Перед кадром
    (`renderFrame`) и после компоновки (`layoutFrame`, до 3 проходов вместе с окнами виртуальных списков)
    `ExpressionBindings::update` сначала переносит правки пользователя в источники двусторонних привязок
    (переменная или поле записи), затем сравнивает зависимости каждой привязки с запомненными — строки свойств
    и номера версий переменных и моделей, без вычисления XPath — и вычисляет заново только изменившиеся; запись
    в узел — только при новом результате. Встраивать уведомления в каждый путь изменения узла (ввод, код,
    компоновка) не нужно, а кадры и так рисуются только по событиям.
  - Владелец — `ListBindings` (как и привязки списков): копии шаблонов получают выражения через тот же `bind`,
    удаление узлов снимает их через `forget`; `gran_snapshot` вычисляет выражения без окна.

- **Компоненты** (`markup/component_*`). Библиотека — отдельный файл `<Library namespace>` с `<Style>` и
  `<Component name>` (`<Param>`, свои `<Style>`, тело — один элемент, `<Slot>`); окно подключает её `<xi:include>`
  в конце `<Resources>`. Включение делает загрузчик (`loadComponents`), а не `processXInclude` парсера: в DOM окна
  остаётся сам `<xi:include>`, и сохранение не вклеивает библиотеку. Встроенная схема знает `<Library>` как второй
  глобальный элемент (файл библиотеки проверяется той же схемой), `<Slot>` и `xs:any ##other` (lax) в группе
  элементов интерфейса — экземпляр `<w:Card>` проходит её как «элемент другого пространства имён».
  - Схема: на каждую библиотеку генерируется XSD (`component_schema.cpp`, `targetNamespace` = namespace, `xs:import`
    без адреса, типы и группы `gran-ui.xsd`), `Schema::fromDocuments` собирает её вместе со встроенной; ею
    проверяются окно и все библиотеки (экземпляры в телах) при загрузке, во фрагментах `appendMarkup` и при каждой
    живой правке (`documentSchema`). Схема живёт в `UiDocument::components` (`ComponentSet`: библиотеки с DOM,
    объявления `ComponentSpec`, общая схема).
  - Развёртка (паттерн Prototype): экземпляр → копия тела в своём документе «Берёсты» (`makeShadow`) с подстановками
    (`Substitution`): `{$параметр}` целиком — значение экземпляра как есть, внутри выражения — значение XPath
    (строка, число, `true()`, выражение экземпляра в скобках, смешанный текст через `concat`), локальные id →
    «приставка.id» (и в `$id.свойство`, `labeledBy`, `popup`), `style` → имя в наборе стилей документа (свои стили
    регистрируются как `_N.Компонент.Стиль`, стили библиотеки — `_N-Стиль`), атрибуты хозяина — поверх корня.
    Копия строится обычным `buildNode`, так что привязки, события, команды, списки и доступность работают
    без особых случаев. Корень развёртки ссылается на элемент экземпляра (`domElement`) и владеет копией
    (`ui::Node::expansions` — объявлено до `children`, поэтому дети уничтожаются раньше копии).
  - Слоты: `BuildContext::scope` — цепочка развёрток (`ComponentScope`: компонент, экземпляр, внешняя развёртка).
    Содержимое слота строится в области `outer` — там, где написан экземпляр: его элементы — настоящие элементы
    DOM окна (их правка работает как обычно), вложенный `<Slot>` пересылает слот внешнего компонента. Рекурсию
    (компонент уже в цепочке) ловит `expandComponent`.
  - Живой документ: правка атрибута экземпляра — обычная перестройка узла; элементы тела живут в копии, поэтому
    `editMarkupAttribute` их отвергает (владелец элемента — не DOM окна). Частичная перезагрузка требует равных
    библиотек (`sameComponents`); экземпляр сравнивается как любой элемент: равное поддерево оставляет развёртку,
    иначе экземпляр перестраивается. `Application` следит за файлами библиотек вместе с главным (`reload_libraries.cpp`).

## 4. Отрисовка

D3D11 — дополнительный бэкенд FL11_0/SM5 с теми же структурами сцены и HLSL (DXBC через fxc).
В нём нет безлимитного массива SRV: атлас, рампа и подложка привязаны постоянно, смена картинки
делит сегмент на последовательные пакеты. Снимки, WARP и Kawase-подложки поддерживаются обоими API.
`AUTO` сначала создаёт D3D12 и при ошибке создания пробует D3D11; явный выбор API сохраняется.
Перезагрузка XML заменяет дерево на границе цикла и отключает старые ссылки ввода и UIA;
окно и GPU-бэкенд продолжают жить. Подробности — [API](api.md).

- **Один шейдер-«убер» и один instanced-вызов**: квадрат строится из `SV_VertexID`, данные — из
  `StructuredBuffer<GpuInstance>`; вид экземпляра (прямоугольник, тень, глиф, картинка, подложка) — поле `kind`.
  Текстуры — «безлимитный» массив дескрипторов (индекс в экземпляре), поэтому смена текстуры не рвёт пакет.
- **SDF скруглённого прямоугольника** с раздельными радиусами углов, рамкой, заливкой цветом или градиентом
  (линейный, радиальный, конический; рампа на 256 текселей в атласе рамп), сглаживание аналитическое (без MSAA).
- **Тени** `box-shadow` (внешние и внутренние): гауссово размытие скруглённого прямоугольника в замкнутой форме.
- **Размытие подложки**: копия цели → двойной Kawase (вниз/вверх) → экземпляр `BACKDROP` берёт размытую текстуру
  со своей маской и тонировкой.
- **Отсечение** скруглёнными прямоугольниками — SDF в пиксельном шейдере по индексу из таблицы отсечений,
  без смены состояния и без scissor.
- **Текст** — атлас покрытия R8: глиф растеризуется на CPU точным интегралом площади под квадратичными кривыми
  на нужном размере и с подпиксельным сдвигом (¼ px), как в браузерах; большой и масштабируемый текст — позже SDF.
- **Цвет и смешивание** — в sRGB, предумноженная альфа (как в браузерах).
- **Кадры в полёте** — 2, кольцевой буфер загрузки, отложенное удаление; правила — [docs/development.md](development.md#правила-работы-с-видеокартой).

## 5. Компоновка (предсказуемая модель)

- Блок: `margin` (без схлопывания) → `border` → `padding` → содержимое. `width`/`height`: `auto`, пиксели, `%`.
  `minWidth`/`maxWidth`/`minHeight`/`maxHeight` всегда соблюдаются.
- `Stack`: `orientation`, `spacing`, `justify` (`start|center|end|space-between|space-around|space-evenly`),
  `align` (`start|center|end|stretch`), у детей `grow`, `shrink`, `alignSelf`; `wrap`.
- `Grid`: `rows`/`columns` — список дорожек (`48`, `auto`, `1fr`, `minmax(100,1fr)`), `rowSpacing`/`columnSpacing`,
  у детей `gridRow`, `gridColumn`, `gridRowSpan`, `gridColumnSpan`.
- `Canvas`: `left`/`top`/`right`/`bottom` у детей.
- Стек с растущим ребёнком (`grow`) при конечном месте занимает его целиком уже при измерении: поперечные
  размеры (высота текста с переносом) меряются по итоговым длинам, а не по базовым.
- `Popup` вынут из потока (как `position: fixed`): меряется по окну и встаёт у якоря (под ним, над ним при нехватке
  места, у точки — с отражением внутрь окна).
- Один проход измерения + один проход размещения; кэш измерений по ограничениям.
- **Локальная перекомпоновка.** `markDirty(узел, DIRTY_LAYOUT)` поднимает флаг ко всем предкам, поэтому узел без флага —
  неизменившееся поддерево. Его измерения (два последних размера доступного места) живут между проходами, а при
  размещении ветвь того же размера не пересчитывается: при том же месте — ничего, при новом — рамки поддерева только
  сдвигаются. Правка одной записи в списке из 10 000 стоит ~1 мс вместо ~60 мс. Суммы главной оси стека — в `double`,
  свободное место в пределах погрешности округления считается нулём: иначе длинный стек «сжимался» бы на доли пикселя,
  и каждый элемент перемерялся бы заново.
- **Виртуальные списки** (`virtual="true"`, модуль `binding/`). Копии шаблона есть только у окна записей около видимой
  области прокрутки; записи до и после окна заменяют две распорки-`Box` размером «число записей × средний размер».
  После компоновки `ListBindings::updateVirtual` подгоняет окно (пересекающееся — по краям, остальные копии живут),
  и в том же кадре идут ещё проход стилей и компоновка (`app::layoutFrame`, не больше трёх). Распорки меняются
  только при разнице больше полупикселя — дрожание среднего не перекомпоновывает список.

## 6. Производительность (цели)

| Метрика | Цель |
|---|---|
| Холодный старт окна с формой из 200 элементов | < 30 мс до первого кадра |
| Разбор + проверка схемы + стиль + компоновка 1 000 элементов | < 2 мс |
| Кадр при анимации (CPU) | < 1 мс, 1 вызов отрисовки |
| Память процесса с открытым окном | < 20 МБ (без драйвера); драйвер AMD для D3D12 сам берёт ~92 МБ, D3D11 — ~34 МБ |
| Простой | 0 % CPU, 0 кадров |

## 7. Этапы

1. Каркас, правила, сборка (Makefile + CMake), тесты, каталог сообщений.
2. Значения стилей, схема XSD 1.1 с утверждениями, загрузка разметки в дерево UI.
3. Каскад стилей, компоновка Stack/Grid/Canvas.
4. Список отрисовки, экземпляры, Null-бэкенд.
5. D3D12 + Win32: окно, шейдер, тени, градиенты, отсечения; снимки вне экрана в PNG.
6. Текст: TrueType, растеризация, атлас, кернинг, перенос строк.
7. Ввод: hover/pressed/focus, переходы, поле ввода, прокрутка.
8. PNG, картинки; размытие подложки.
9. Vulkan 1.0 + X11 на Linux (реализовано): GPU/CPU Mesa, фиксированные дескрипторы, два кадра,
   deferred release, swapchain/offscreen/readback и общий HLSL/Kawase. SDK нужен при сборке; macOS отложен.
10. Замеры против Chromium/Electron и WebView2.
