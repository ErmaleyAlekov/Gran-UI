## Каталоги

| Каталог | Что внутри |
|---|---|
| `include/gran/<модуль>/` | Публичные заголовки; `internal/` — заголовки для своих файлов модуля |
| `src/<модуль>/` | Реализация, зеркально `include/gran/` |
| `schemas/` | Схема разметки `gran-ui.xsd` и тема по умолчанию `default_theme.xml` (встраиваются в библиотеку) |
| `shaders/hlsl/` | Исходники шейдеров; байт-код — `src/rhi/shaders_gen/` (генерируется) |
| `samples/` | Разметки для опытов и проверки кадров |
| `examples/` | Программы: `gallery`, `snapshot`, `chat`; каждая папка — программа `gran_<имя>` |
| `tests/` | Модульные тесты (`tests/src/<модуль>/`) и свой маленький тестовый каркас |
| `tools/embed/` | `gran_embed` — превращает файл в массив C++ |
| `cmake/` | Части сборки CMake: параметры, списки исходников, шейдеры, чтение версии из `gran_version.h` |
| `docs/` | Документация |

Модули и конвейер описаны в [архитектуре](architecture.md). Префикс `gran/` в путях заголовков нужен, чтобы
не пересекаться с заголовками «Берёсты» (`core/`, `utils/`).

## Тесты и проверка кадров

```bash
make test
```

`gran_tests` собирает все наборы из `tests/src/` (стили, разметка, компоновка Stack и Grid, выделение текста,
поля, всплывающие слои, доступность, UTF-8, PNG, каталог сообщений, а также переносимая часть примера чата:
JSON, chunked, NDJSON, Markdown). В CMake те же тесты запускает `ctest`.

Набор тестов объявляется в `tests/include/suites/test_suites.hpp` функцией `register<Набор>Tests(test::TestRunner&)` и добавляется в список `tests/src/main.cpp`; проверки —
макросы `TEST_ASSERT`, `TEST_ASSERT_EQ`, `TEST_ASSERT_NEAR`, `TEST_ASSERT_THROWS`.

Отрисовку проверяет кадр вне экрана: `gran_snapshot <разметка.xml> <кадр.png>` рисует разметку через
Direct3D 12 без окна, с включённым отладочным слоем, и печатает время этапов. Изменения сцены и шейдеров
сверяются с прежним кадром пиксель в пиксель.

### Санитайзеры и отладочные слои

| Что | Как запустить |
|---|---|
| ASan + UBSan (Linux, GCC/Clang) | `make DEBUG=1 SANITIZE=address,undefined test` |
| TSan (Linux) — для кода с потоками | `make DEBUG=1 SANITIZE=thread test` (с `address` не сочетается) |
| ASan (Windows, MSVC) | `cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DGRAN_SANITIZE=address`, затем `ctest` |
| Valgrind memcheck (Linux) | `valgrind --error-exitcode=1 bin/gran_tests` (сборка без санитайзеров) |
| D3D12 Debug Layer + GPU-Based Validation | `GRAN_GPU_VALIDATION=1 bin/gran_snapshot <разметка> <кадр.png>` (слой включён всегда, GBV — по переменной) |
| Vulkan Validation + synchronization validation | `make DEBUG=1`, слой `VK_LAYER_KHRONOS_validation` подключается сам, если установлен |

MinGW санитайзеры не поддерживает — на Windows только MSVC. Любое сообщение санитайзера или отладочного слоя —
ошибка, а не шум. Исключение — утечки самого драйвера Vulkan (Mesa lavapipe) в тесте окна Linux: они перечислены
в `tests/linux/lsan_mesa.supp` (`LSAN_OPTIONS=suppressions=tests/linux/lsan_mesa.supp bin/gran_linux_tests --window`),
а в стеке оставшихся не должно быть ни одного кадра Грани.

### Ручные проверки

Часть проверок делает человек: живое окно, вид кадра, захват кадра в RenderDoc или PIX, отладчик, долгие сессии,
реальные видеокарты. Задачи с точными шагами готовятся после каждой большой доработки — [tests/manual](../tests/manual/README.md).

## Правила кода

Код движка пишется по единым правилам — их соблюдают и человек, и модели:

- **C++17**, стандартная библиотека и системные SDK; никаких сторонних библиотек. Парсеры (TrueType, PNG,
  inflate, значения стилей, JSON в примере) — свои.
- Тело функции — не длиннее **25 строк** кода, в файле реализации — не больше **5 функций**, у функции — не больше
  **5 параметров** (больше — структура параметров).
- В заголовках — только объявления; вся логика — в `.cpp`.
- **Комментарии на двух языках:** сначала русский, затем тот же смысл по-английски. Комментарии стоят перед
  каждым классом, функцией и неочевидной веткой.
- Тексты, которые видит пользователь, не пишутся литералами — только идентификатор сообщения из каталога.
- Тернарные операторы и лямбды — только когда без них код становится сложнее.
- Свои классы исключений (`GranException` и наследники) с кодом ошибки.
- Сборка — одновременно Makefile и CMake, без изменений на Windows, Linux и macOS (там, где есть платформа).

## Правила работы с видеокартой

Ошибка в работе с памятью видеокарты не падает сразу: она портит кадр или «теряет» устройство через минуты.
Поэтому:

- **Владение объектами GPU** — только через обёртки (`ComRef<T>` для D3D12/DXGI); обёртки не копируются,
  только перемещаются. Ресурс, побывавший в командном списке, удаляется через очередь отложенного удаления —
  когда забор (fence) кадра, где он использовался последним, пройден.
- **Кадров в полёте — два:** у каждого свой командный аллокатор, участок кольцевого буфера загрузки и значение
  забора. Никаких «на всякий случай» ожиданий простоя в обычном кадре.
- **Каждый `HRESULT` проверяется** макросом `GRAN_CHECK_HR`, который бросает `GpuException`. Потеря устройства —
  штатное событие: сцена целиком хранится на CPU, видеокарта — только кэш.
- **Границы памяти:** любая запись в буфер GPU проверяется против ёмкости до записи. Структуры, общие для C++
  и HLSL (`GpuInstance`, `FrameConstants`), — из 4-байтовых полей, размер кратен 16, `static_assert` на размер
  и смещения; в HLSL рядом — комментарий со смещениями. Меняется структура — меняются оба файла.
- **Шейдеры** — один исходник HLSL, компиляция `dxc` при сборке; в коде движка компиляции шейдеров нет.
- Каждому объекту GPU даётся имя (`SetName`) для PIX и RenderDoc.
- Объекты GPU создаются и уничтожаются в потоке рендера; оконная процедура только складывает события в очередь
  и не бросает исключений.

## Как добавить элемент

1. Схема: тип элемента и его атрибуты в `schemas/gran-ui.xsd` (ограничения — через `xs:assert`).
2. Вид: значение в `ui::ElementKind` (`include/gran/ui/node.hpp`), имя элемента — таблица `NAMES`
   в `src/ui/node.cpp`, разбор атрибутов содержимого — `src/markup/node_content.cpp`.
3. Оформление по умолчанию — `Style` с именем элемента в `schemas/default_theme.xml`.
4. Компоновка — `src/layout/`, отрисовка — `src/render/scene/`, ввод — `src/input/`, роль для доступности —
   `src/a11y/`.
5. Тест в `tests/src/<модуль>/` и разметка в `samples/` для проверки кадром.

## Сообщения и языки

Каталог сообщений — `src/core/i18n/catalogs/messages_ru.cpp` и `messages_en.cpp`; идентификаторы —
`include/gran/core/message.hpp`. Новый язык — ещё один файл каталога. Язык во время работы меняет
`gran::i18n::setLanguage("en")`. Ошибки «Берёсты» (разбор XML и схема) приходят на её языке, со строкой,
столбцом и путём к элементу.

## Отладка

Горячая перезагрузка — `gran_gallery --watch`, выбор API — `--d3d11` / `--d3d12`.
[Справочник API](api.md) описывает ограничения времени жизни узлов, [GPU-проверки](render_testing.md) —
снимки обоих бэкендов и команды `make test-render` / CTest.

- Отладочная сборка: `make DEBUG=1` или `-DCMAKE_BUILD_TYPE=Debug` (`GRAN_DEBUG=1`).
- Отладочный слой D3D12: ключ `--debug` у `gran_gallery`, всегда включён у `gran_snapshot`; переменная
  окружения `GRAN_GPU_VALIDATION=1` добавляет GPU-Based Validation. Сообщения слоя уходят в журнал движка.
- Выбор видеокарты: `GRAN_ADAPTER=<часть имени>` (без учёта регистра: `intel`, `nvidia`, `RTX 3060`) — для D3D12,
  D3D11 и Vulkan. Без переменной D3D12 и Vulkan берут самую производительную карту, D3D11 — первую в списке DXGI.
  Нет подходящей карты — ошибка со списком найденных, без перехода на WARP / lavapipe; при `--warp` переменная не действует.
- `gran_gallery --exit-after N` закрывает окно через N секунд — удобно для проверок без участия человека.
- Кадр с видеокарты разбирается в PIX или RenderDoc: у всех объектов есть имена.
